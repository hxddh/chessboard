## 0 · 这一版为什么长这样

6.1 把 6.0 的账本核到底，代价是它整版都在还债。核完之后剩下的问题换了性质：

**能力已经堆得很齐，但它们没有连起来。** 这个应用有完整的分析树、胜率口径的
复盘、Glicko-2 评级、SRS、母题识别、错题自炼、开局树——每一件单独看都做得
扎实。可是 `mistakes.js` 的文件头自己写着这句话：

> 「任何现成题库都给不了的那一种内容，是这个玩家真正输掉的那些棋。」

说得对。而今天这条回路**只对在这个应用里下的棋成立**，而且一次只能分析一局
（`analyzeGame` 只作用于当前局面，入口就两个按钮）。任何人 99% 的对局在别处，
导进来还得先「选一局」。也就是说：这个应用最有说服力的那句主张，落地覆盖率
接近于零。

7.0 只有一条主线：**把玩家自己的棋批量吃进来，变成诊断和训练。** 其余的修复
按危害排序附在前面——其中一条是 6.1 自己捅的，必须先补。

审计同时确认了几件做得好的事，写下来是为了不在下一轮重复怀疑：三语 805 个键
完全对齐、占位符零不一致；`game-tree.js` 16 万次随机编辑后零不变量破坏；
6.0 → 6.1 的题目 id 全部保留（958 道一道没丢），老用户的进度不会变孤儿。

## 1 · 丢档：注释里的 `}` 会让文件再也打不开（P0，6.1 自己引入）

6.1 修评审提的「外部 PGN 里以反斜杠结尾的注释」时，我给花括号注释的扫描器加了
一条启发式：私有转义的读法只在「它多吞的那一段里不含 `{`」时才胜出，理由写的是
「我们自己的输出永远不会有」。**这句话是错的。**

随机往返模糊测试三个种子都稳定复现。最小复现（注释内容 → 往返结果）：

| 注释内容 | 序列化成 | 读回来 |
|---|---|---|
| `}{` | `{ \}{ }` | `\` —— 静默截断 |
| `}  {` | `{ \} { }` | `\` —— 静默截断 |
| `a}b{c` | `{ a\}b{c }` | **整份文件解析失败** |
| `}}{{` | `{ \}\}{{ }` | **整份文件解析失败** |
| `} [%cal Ge2e4] {` | `{ \} \[%cal Ge2e4] { }` | **整份文件解析失败** |

只要注释里出现一个 `}`、后面再出现一个 `{`，这份 PGN 就不是被截断就是打不开。

**危害面**：存档槽位存的就是 PGN 文本（`app.js` `saveToSlot` → `pgn:
pgnForExport()`），读回走 `importPgnText`。所以玩家在批注里打了这两个字符，存进
槽位，那一局就**永久读不回来了**。导出的文件同理。（自动保存同时存了树的 JSON，
所以那条路有救；槽位和文件导出没有。）

### 修法：让导出不再产生「需要跨过 `}`」的转义

PGN 本身在花括号注释里没有转义，第一个 `}` 就结束——这是不可协商的。任何私有
转义都会和外部文件撞车，6.1 的单遍启发式两个方向都保不住。所以改成：

- **导出**：`\` → `\\`，`}` → `\R`，`[%cal`/`[%csl` → `\[%cal`/`\[%csl`。
  序列化后的注释里**一个字面 `}` 都没有**。
- **导入**：按规范扫描（第一个 `}` 结束，不做任何转义判断），然后宽容反转义——
  只认 `\\`、`\R`、`\[`，其余反斜杠原样保留。

这样外部文件**永远不会被截断或吞掉着法**（那是重要的性质），代价是外部注释里
恰好出现 `\R` 会显示成 `}`——一处观感损坏，有界，不影响结构。

- **旧档兼容**：6.0/6.1 导出的文件里是 `\}`。规范扫描会在那里提前结束，导致
  解析失败。所以加一层**文档级回退**：按规范读整份文件，若抛错则用旧的转义感知
  读法重读一遍。一次性的，读得进就行，写出去一律用新编码。

**验收**：把这次的模糊测试固化成 `scripts/test-pgn.mjs` 的一节——随机生成带
注释/NAG/变着/箭头的树，往返必须逐字段相等，种子写死可复现。外加上表五条各一条
断言，和一条「6.1 格式的文件仍读得进」的语料。

## 2 · 题库：11% 的题会把下对的人判错（P0）

`tac`（589 道）和 `win`（305 道）走 **SAN 精确匹配**判题。这两类占挖掘题的 87%、
占玩家能遇到的题的绝大多数。而代码里其他每一类都不这么干，且都在注释里写清了
理由：

- `real`：「一个 25 子的局面里后续通常有好几手同样好，把其中一手判错，教的是
  这堂课的反面」
- `def`：「坚持某一手存着的着法，会把一个完全过硬的防守判错」
- `mine`：走别的着法时用引擎按原预算复核，差距在一个「失误」以内就判对
  （`verifyMineAlt`）

`tac` 和 `win` 没有这层保护，而且它们从来没有被深搜复验过——`test-tactics.mjs`
只加载 `puzzles.js` 里 `cat === "real"` 的 23 道；1023 道挖掘题**一道都不在
CI 的正确性门禁里**。挖掘时的筛选是 120 毫秒、120 厘兵。而 `test-tactics.mjs`
自己的文件头就写着为什么这不够：「生成器筛 350 毫秒，深搜复验时头一批候选里有
三道其实有第二解。」

### 量出来的比例

894 道 tac+win 里随机抽 140 道，`go depth 18`、MultiPV 2 复验：

| | 道数 | 占比 |
|---|---|---|
| 干净 | 124 | 89% |
| 存在同等好的第二解（差 < 50 厘兵） | 8 | 6% |
| **存的答案根本不是引擎首选** | 8 | 6% |

合计 **11%**（95% 区间约 7%–18%，推到全体约 60–160 道）。样例：

```
[tac] mn-203-125-47  存 Rxd7  引擎 Rf6    差 262cp   存的答案明显更差
[tac] mn-202-25-35   存 Nxc7+ 引擎 Nd6+   差 120cp
[tac] mn-201-40-78   存 Qc2   引擎 Qxg4   差 111cp
[tac] mn-302-73-61   存 c8=Q+ 引擎 c8=R+  差   2cp   低升变同样好，走 R 被判错
[tac] mn-201-46-81   存 Rb1+  引擎 Rh7+   差   0cp
```

判错不只是一句提示：它同时喂给 SRS（题目重新入队）和 Glicko-2（玩家评级被下调）。
**玩家因为找到一步同样好的棋而被扣分，然后被要求把这道题再做一遍。** 最后一行
那种更糟——应用在教一步更差的棋。

### 修法（三件，缺一不可）

1. **判题接受同等好的着法。** 把 `verifyMineAlt` 抽成通用的 `verifyAlt`——它
   本来就只比较「走存的答案之后」与「走这一手之后」的评估，mine 专属的只有一个
   预算字段。`tac`/`win` 第一手走别的着法时走同一条路：差距在一个「失误」以内
   判对，并提示「这手也行」。多手题的后续仍按剧本，和 `real` 的理由一致。
2. **补上 CI 的正确性门禁。** 新增 `scripts/test-mined.mjs`：对全部 894 道
   tac/win 做 `go depth 18` 双线复验，断言存的答案是首选、且领先次优 ≥ 50 厘兵。
   进 `test:engine`（release 跑全量），不进 PR CI（太慢）。这次评审用的临时脚本
   就是它的雏形。
3. **按门禁清理现有题库。** 存的答案不是首选的，用引擎的首选改写或直接退役；
   有同等好第二解的，把第二解记进 `accept` 字段（`Mistakes.isAccepted` 已有
   这个概念，扩展到题库即可）。**题目 id 不得变动**——6.0 → 6.1 保住了 958 道
   id 的连续性，这一版同样不能让老用户的进度变孤儿；退役的题走 `dropped` 那条
   已有的清理路径。

**验收**：门禁通过；被改写/退役的题逐条记进 `docs/measured.json`；再抽 140 道
复验，问题率必须 < 2%。

## 3 · 评级不会随时间松动（P1）

`rating.js` 的文件头写着选 Glicko-2 而不是 Elo 的理由：

> 「一个玩家可能离开一个月。Elo 不记得自己有多确定……Glicko 带着偏差 `rd`，
> Glicko-2 再加上波动率 `vol`，这正是让一个回归玩家的评级能重新快速移动的东西。」

`update()` 里确实有那条分支（无对局时只让 `rd` 增长）。**全仓库没有任何地方
调用它。** 整个应用只调 `rate1v1`，而那条路每次都在收紧 `rd`。

实测（答 400 题后）：`rd` 稳定在 61 左右——所以评级本身还是能动的（连对 60 道
1800 分的题，从 1215 走到 2024），我原先担心的「评级冻结」不成立，这里更正。
真正的问题是另一半：**离开三个月回来，系统仍以 `rd ≈ 61` 宣称对那个陈旧数字很有
把握**，「为你出一题」照着一个三个月前的区间出题。文档承诺的那件事没有兑现。

**修法**：记录上次答题时间，开场按闲置天数结算若干个「无对局评分期」
（`update(player, [])`），并给 `rd` 封顶在初始的 350——比新玩家还不确定是没有
意义的。**验收**：单测钉住「闲置 30 天后 `rd` 明显回升且不超过 350」，
以及「回归后 10 题内评级的移动幅度显著大于不衰减的情形」。

## 4 · 把不敢背书的标注从界面上撤下来（P1）

6.1 量到 `?!` 在 120/400/1200 三档预算下的两遍重合率只有 52/56/54%，写下了
「`?!` 是这个应用唯一不敢背书的标注」。**但界面上它仍和 `?`、`??` 完全同等地
显示。** 一个自己承认接近抛硬币的判断，不该和 97% 可复现的判断长得一样。

**修法**：着法表里 `?!` 降格——换一种明显更弱的呈现（灰、细、不进统计徽章），
或直接只在「显示存疑标注」开着时出现，默认关。精准度与 ACPL 的计算不变（那是
连续量，不受档位噪声影响），变的只是那个**离散断言**的呈现。README 与关于面板
同步写明理由。**验收**：布局 e2e 断言 `?!` 与 `?`/`??` 的呈现不同类。

## 5 · 白方第一手不计时，还白拿一次加秒（P2）

`clockRunning()` 要求 `sanHistory().length >= 1`，所以开局白方想多久都不走钟；
黑方从第一手起就走钟。而 `applyIncrement` 在那一手之后照样给白方加上 Fischer
增量——一次没花时间的移动换来 +2/+3 秒。注释说的「别让人在开始画面上漏钟」是
对的，但实现连带把白方的第一手也豁免了。

**修法**：钟从**进入对局且有时限**时开始走（或首次落子/首次与棋盘交互，取先到
者），第一手的增量按常规结算。**验收**：时钟 e2e 加一条——白方第一手耗时必须
计入白方。

## 6 · 主线：把玩家自己的棋批量吃进来

前面五条是修，这一条是这一版存在的理由。

### 6.1 批量导入与离线分析

今天：`importPgnText` 遇到多局文件让你**选一局**；`analyzeGame` 只分析当前局。
想分析自己 200 局在线对局，要手工重复 200 次。

新增**棋谱库**：一次导入整份多局 PGN（lichess / chess.com 的导出就是这个格式），
落进本地档案；后台按 120 毫秒/手逐局分析（200 局 × 80 手 ≈ 30 分钟），可暂停、
可续跑、关掉应用不丢进度。分析结果和对局一起存，不用重算。

技术上全部是现成件的组合：`pgn-parser.js` 的 `splitGames` 已经能切多局、
`analyzeGame` 的主循环已经能断点续传（`analyzeAbort` 保留前缀）、`persist.js`
已经能把整份档案镜像到壳层。**要写的是调度和存储，不是新算法。**

### 6.2 诊断：从一堆数字到一句话

有了几百局的分析，才第一次能说出有统计意义的话。报告页新增「你的棋」：

- **分阶段精准度**：开局 / 中局 / 残局各自的胜率口径精准度。「你的残局比中局低
  18 个点」是一句能直接决定练什么的话，而单局复盘永远给不出它。
- **按母题的失误率**：`motif.js` 已经能从局面认出捉双/牵制/串击/闪将/双将。
  统计「你被捉双打中的频率是其他失误的 3 倍」。
- **按开局的战绩与失分点**：`eco-lookup.js` 已经能按局面认开局（3810 个局面）。
  「你执黑对 e4 的 12 局里输了 9 局，平均在第 11 手掉分」。
- **崩盘位置分布**：失误在第几手最密集——配合时限能看出是不是时间恐慌。

每一条都必须**点到一个可执行的下一步**：一道同母题的题、一课、一条开局线。
没有下一步的统计不写进这一页。

### 6.3 错题自炼扩容到真实规模

`MAX_MINES = 50` 是按「每天下几局、一局几个失误」定的。批量导入之后，来源
从「这个应用里下的几局」变成「你全部的棋」，50 这个数和它的淘汰策略都要重估：
按母题分层保留（每个母题留最近 N 道），而不是单纯按时间淘汰，否则一次导入会把
一个月积累的错题全冲掉。

### 6.4 解释，而不只是打分

今天复盘说「第 23 手 ?? 亏了 4.1」。这句话告诉你错了，没告诉你**错在哪**。

`motif.js` 已经在做母题识别，`review.js` 已经有引擎的首选着法和后续变化。把
两者接起来，让失误带一句话：「走 Nf3 之后，黑方 e4 的马同时叫你的后和 h2 的
车——捉双」。做不到可靠识别的局面就不说，**宁可不说也不要说错**——这是这个
仓库一贯的规矩，一句猜出来的解释比一个数字糟得多。

**验收**：在 28 局语料上，能给出解释的失误比例要量出来并写明；抽样人工核对
解释的正确率，低于某个门槛就默认关掉这个功能并如实记录。

## 7 · 底层依赖：升上去能拿到什么，怎么把它用足

两个包都下下来逐文件比对过，Stockfish 直接跑了头对头。**上一稿这一节有两处判断
错了，下面一并更正**——`.persist` 和 `core.store.*` 我当时以为 WebView 应用能用，
实际不能。

| 依赖 | 现在 | 最新 | 结论 |
|---|---|---|---|
| **@native-sdk/cli** | 0.8.1 | **0.10.1** | 升，能力最多 |
| **Stockfish wasm** | 18 lite-single | **19 lite-single** | 升，体积降 75% |
| Zig | 0.16.0 | 0.16.0 | 已最新，不动 |
| esbuild | 0.28.1 | 0.28.2 | 补丁 |
| Playwright | 1.62.1 | 1.63.0 | 小版本 |
| chess.js（vendored） | 0.x（2022） | 1.4.0 | **不升**，见 §7.8 |
| lichess chess-openings | 生成时的提交 | — | 重跑 `gen-eco.mjs`，无风险 |

### 7.1 先讲清楚能力开关的机制，后面每一条都靠它

`app_runner/root.zig` 按 `app.zon` 的 `capabilities` 列表在 **comptime** 决定编进
什么（`manifestDeclaresStore` / `manifestDeclaresSqlite` / `manifestDeclaresCredentials`）：

- `"store"` → `RecordStore`：键值库，前缀扫描、批量写，开在应用数据目录
- `"sqlite"` → `RelationalStore`：SQLite，带迁移、分页查询、变更通知
- `"credentials"` → 钥匙串（这个应用没有账号，不要）

**声明了才编**——所以 9.5 MB 的 `sqlite3.c` 不是强制成本，可以只要 `store` 不要
`sqlite`。这回答了上一稿留的那个疑问。

两个存储的 binding 进的是 runtime options，也就是 **Zig 侧**。页面拿不到：
`native-sdk.*` 的完整命令表里没有任何存储命令。要给页面用，得像今天的
`chess.appdataRead/Write` 一样，自己在 `main.zig` 写一层 `chess.db*`。

> **更正**：上一稿说「`core.store.*` 有桥命令，页面直接能调」是错的。那几个名字
> 出现在 `src/runtime/effects.zig`，是确定性 core 的**效果名**，不是 WebView 的
> 桥命令。

### 7.2 更正：`.persist` 用不了，手写那套继续留着

`.persist`（`version` / `debounce_ms` / `restore.ok·none·err`）的消费者是
`ts_core_main.zig`、`ts_ui_app.zig`、`ui_app.zig` —— 确定性 core 那条路线。
`app_runner/root.zig`（本仓库 `runner.zig` 分叉的那个）里 **`persist` 一次都没出现**。
`core.persist.flush` 同理。

所以上一稿写的「SDK 现在自带 persist.js 那套」是误判。`persist.js` 继续留着，
它的 `.bak` 回退、隔离区、以及 6.1 补的「读不出来的文件整场闸死镜像」都没有替代品。
§1 的丢档修复照原计划做。

### 7.3 `.updates`：白拿一整条签名自动更新

在 `app.zon` 声明三个字段：

```zig
.updates = .{
    .feed_url = "https://…/appcast.json",   // 必须 https
    .public_key = "<base64 的 32 字节公钥>",
    .check_on_start = true,
},
```

宿主（`src/platform/macos/appkit_host.m`）就给出整条链路：拉取签名源 →
**Ed25519 验签** → 弹「Install Update」→ 带进度条下载（可取消）→
**SHA-256 校验归档** → 安装。菜单里多一个标准项，命令名 `app.check-for-updates`。

**能删掉的**：`main.zig` 里手写的 `chess.checkUpdate`（连同那个 `std.http.Client`
和 `formatLatestRelease`）、`host.js` 里的 5 秒竞速、页面侧的版本比对。今天这套
只问 GitHub 要个 tag，**不下载、不验签、不安装**，用户得自己去下载替换。

**为什么这件事比看起来重要**：它和代码签名是**两套信任根**。应用内置公钥、更新源
用私钥签名，不需要 Apple 或微软的任何证书，就能保证「这个更新是我发的、没被掉包」。
——但它**不能替代公证**，首次打开仍要右键过 Gatekeeper。这两件事别混为一谈。

**要做的事**：生成 Ed25519 密钥对；私钥进 GitHub Actions secret；`release.yml`
多一步生成并签名 feed JSON，发到固定 URL（GitHub Pages 或 release 资产均可）。

**待核实的坑**：宿主的弹窗文案是硬编码英文（`"Install Update"`）。一个中文优先的
应用弹出英文对话框是要解决的——实现时先确认能否本地化，不能就在 README 与
`docs/manual-check.md` 里写明这条已知差距，**不要装作没看见**。

### 7.4 SQLite：§6 的棋谱库该建在它上面

今天 `persist.js` 是「整份档案一个 blob、400 ms 防抖、全量重写」。存几 KB 设置
没问题；存 200 局 × 80 手的分析数组，每次改动都要重写整个几十 MB 的 blob，这个
设计会直接塌掉。

`RelationalStore` 给的正好是缺的那些：迁移（`src/schema/migrations.lock.json`，
构建时生成 `migrations.zig`，**需要 node 在 PATH 上**）、分页查询
（`default_page_rows = 256`）、变更通知（`ChangedTable` / `ChangeBatch`）。

**分界线要划清楚**：档案（设置、当前对局、错题本、SRS 状态）继续走 `persist.js`
那条已经被两版打磨过的路；**只有棋谱库这一块新数据进 SQLite**。不要借升级之机
把已经正确的东西重写一遍——那是 6.1 教过的教训。

### 7.5 通知：批量分析终于有了正确的载体

0.10.1 的通知加了 `id`（去重/替换）和 `actionLabel` / `actionCommand`（动作按钮
直接派发应用命令）；0.8.1 只有 `title` / `subtitle` / `body`。

§6 的批量分析要跑半小时，正需要这个：一条固定 `id` 的通知随进度**替换**（而不是
堆出二十条），完成时带一个「查看诊断」按钮直接跳到报告页。

### 7.6 `.file_associations` 与 `.dmg`：三个手工件换成两段声明

今天 `.pgn` 关联是**打包后改 plist**（`scripts/add-pgn-doctype.sh`）加两个 Windows
注册表件（`register-pgn.cmd` / `register-pgn.reg`）；dmg 布局是脚本拼的。manifest
里都有对应的键（`file_associations` 在 0.8.1 就有，`dmg` 在 0.10.1 的 schema 里，
支持卷名、背景、窗口尺寸、图标位置）。换过去少三个手工件，而且跨平台一条声明。

### 7.7 看过、明确不用的

`cef`（用系统 WebView）、`core_compiler` / `service_*`（另一套架构，引擎是页面里的
wasm Worker，搬过去等于重写）、`shell`（多窗口/多页签，仓库明确不做）、
`url_schemes`、`dock_visible`、`webview_layer`、`transparent` / `click_through` /
`always_on_top`、`credentials`（无账号）、tray。

`titlebar = "hidden_inset"` 与 `theme_accent` 是纯外观，可做可不做，**不进这一版的
必做项**——升级版本的风险预算要留给会出事的地方。

### 7.8 Stockfish 18 → 19（lite-single）

40 道挖掘题的战术局面，同一台机器实测：

| | SF18 lite-single（当前） | SF19 lite-single |
|---|---|---|
| wasm 体积 | 7.30 MB | **1.79 MB（−75%）** |
| 启动 | 280 ms | **109 ms（−61%）** |
| `go movetime 120` 找到正解 | 35/40 | 36/40 |
| `go depth 12` 找到正解 | 37/40 | 37/40 |
| 平均 nps | 947k | 627k（−34%） |

SF19 的 lite 用的是一张新的 1 MB 网络（sscg13 的 sf19-1mb），自带、不需要外部
NNUE，UCI 不变，同样 GPLv3。所以这次「更新的 Stockfish」意味着**更小更快，而不是
更强**——nps 反而低了三分之一。

**这个样本不足以下结论，必须写明**：40 道太少，而且这批题当初就是用 SF18 挖出并
筛过的，对 SF18 有系统性偏向。正式评估要跑 `test-strength.mjs`（真对弈）、
`test-tactics.mjs`、`test-novice.mjs`，并且**重跑 6.1 那套复盘噪声测量**——nps 降
三分之一，120 ms 快扫的噪声可能变差，而 `?!`/`?`/`??` 的可复现率正是照着那个预算
量出来的。若噪声确实变差，要么把快扫预算从 120 ms 上调（现在有体积预算可花），
要么如实更新 `docs/measured.json` 和 §4 的结论。

连带必改：`engine-src.js` 现在 9,749,471 字节（wasm 的 base64），换 SF19 后约
2,383,428，而 `sync-dist.mjs` 有一条 `engine-src.js <= 5000000 就失败` 的守卫
（防「打出个空壳」），必须重新标定到 2 MB 上下，否则 CI 当场红。

**chess.js 明确不升**：vendored 的是 0.x 的 snake_case API（`in_checkmate` /
`game_over` / `validate_fen`），1.4.0 全改成 camelCase 且 `move()` 从返回 null
改为抛异常，全仓库约 500 处调用点。而 perft 五组已经证明现有这份是对的，PGN 也
早换成自写解析器——纯机械大改，风险实打实，用户零感知。

### 7.9 7.0-dep：只动依赖的那一版，怎么排

`build.zig` 与 `runner.zig` 是 SDK 两个文件的手抄分叉（`build/app.zig` 1473 →
2895 行、1654 行不同，源文件清单多了 `app_markup.c`、
`native_sdk_macos_info_plist.c`、`third_party/sqlite/sqlite3.c`；
`app_runner/root.zig` 952 → 1397 行）。当年 Windows 未定义符号事故的根因就是
「我们的清单落后上游」，`close_policy` 也曾这样「声明了但没人读」地死在两个版本里。
**这类改动 CI 全绿也可能在真机上悄悄坏掉**，所以它独占一版。

顺序：

1. **Node 22 → 24**（0.10.1 的 `engines` 要求）：六个工作流加 `package.json`。
2. **SDK 0.10.1**：`build.zig` 与 `runner.zig` 逐行重新对齐，不是打补丁。
   `manifest-check.mjs` 必须还绿——它就是为这件事写的。
3. **`.updates`**：密钥对、CI 签名步骤、删掉手写的 `checkUpdate`。弹窗文案的
   本地化问题当场核实并记录。
4. **`.file_associations` + `.dmg`**：删掉三个手工件。
5. **Stockfish 19**：换文件、重标定体积守卫、跑全量 `test:engine`、
   **重跑复盘噪声并更新 `measured.json`**。
6. **esbuild / Playwright** 补丁位。
7. **`capabilities` 加 `"store"`**（先不加 `"sqlite"`）：这一版只把开关打开、
   写一条最小的 `chess.store*` 命令与一条往返测试，**不迁移任何数据**。
   §6 真要用 SQLite 时再加 `"sqlite"`，那时迁移文件和表结构才有意义。

**验收**：全量测试绿、`manifest-check` 绿、双平台**真机走查**（`docs/manual-check.md`
补一节：更新流程、文件关联、dmg 布局、菜单、Esc、close_policy）、噪声重测入账。

## 9 · 建议的取舍

§1–§5 是必须做的，量不大。§6 是这一版的价值所在，但它内部也有优先级：

1. **§6.1 + §6.2 必须一起做**——只有导入没有诊断，等于给了用户一个更大的数据
   坟场；只有诊断没有批量，样本量不够说任何话。
2. **§6.4 单独可上**，风险在「解释可能是错的」，所以它自带一条「量不到就关掉」
   的退路。
3. **§6.3 跟着 §6.1 走**，否则第一次批量导入就会冲掉老错题。

如果工期只够一半：做 §1–§5 加 §6.1/§6.2，把 §6.3/§6.4 留到 7.1。**不要**先做
§6.4——在只有几局样本的时候解释失误，说服力和今天没有区别。

### 和 §7 的关系

依赖升级（§7.9 的 7.0-dep）**排在 §6 前面**，理由不是「先做简单的」，而是三条硬
依赖：

1. §6 的棋谱库要建在 SQLite 上（§7.4）。顺序反了就得先用 blob 写一遍、再迁移一遍。
2. §6 的批量分析要半小时，需要 0.10.1 的可替换通知带动作按钮（§7.5）。
3. Stockfish 19 会改变快扫的噪声特性（§7.8），而 §6.2 的诊断全部建立在那些分析
   数字上——引擎换在诊断之后，等于让刚建立的基线立刻作废。

但**两条 P0（§1 丢档、§2 判错）不等任何东西**：它们在线上正伤人，是独立的、小的，
应该第一个发出去。所以整体顺序是：**P0 补丁 → 7.0-dep → 7.0 主线**。

### 没做到的，逐条

**§7.3 `.updates` 签名自动更新 —— 只接了一半。**
`runner.zig` 的 `appInfo` 现在读 `.updates` 的三个字段（feed_url / public_key /
check_on_start），空字符串就是「更新关着」。**但 `app.zon` 里没有 `.updates` 段，
所以这条链路一次也没通过电。** 缺的是一对 Ed25519 密钥：私钥要进 GitHub Actions
的 secret，而我建不了 secret。手写的 `chess.checkUpdate`（只问 tag、不下载、不验
签）因此原样留着。接上这条的人要做的是：生成密钥对、私钥进 secret、`release.yml`
加一步签 feed JSON、`app.zon` 写上三个字段——`runner.zig` 那一半已经在等着了。

**§7.4 SQLite —— 明确不做，而且计划里的估算是错的。**
计划说 blob 存 200 局分析「每次改动都要重写整个几十 MB 的 blob，这个设计会直接
塌掉」。量了：一局（80 手的 tags / losses / scalars / bests 加头部）是 **2.2 KB**，
500 局上限是 **1.05 MB**，不是几十 MB。差三十倍的原因是计划把 `pvs`（每手一串
SAN）算了进去，而实现没有存它——主变可以随时重算，存下来只是为了省一次搜索。

1 MB 仍然不小：批量分析一趟会重写它几百次。但换 `RelationalStore` 要动
`capabilities`、构建期生成 `migrations.zig`（需要 node 在 PATH）、一套新的桥和
一套新的 JS 侧，而**这些我在这里一次也跑不起来**（见下）。拿一个能测的实现换一个
不能测的实现，不是升级。留给 7.1，前提是那一版有人能在真机上跑。

**§7.6 `.dmg` —— 明确不做。**
`.dmg` 是 `native package --archive` 消费的，而这个仓库的 macOS 流程是
`native package` 打出 `.app` → `add-pgn-doctype.sh` 改 Info.plist 并重签 →
`hdiutil` 出 dmg。`--archive` 在打包那一步就把 dmg 封好了，里面装的是**没有改过
plist 的 .app**。顺序对不上，换过去就是把 `.pgn` 关联从 dmg 里丢掉。

顺带更正一条：`.file_associations` **没有**替掉 `add-pgn-doctype.sh`。打包器只写
`CFBundleDocumentTypes`（`src/tooling/package.zig` 的 `macosDocumentTypes`），
`LSHandlerRank`（不抢默认打开方式）与 `UTExportedTypeDeclarations` 都没有键能
承载。两者互补，脚本的文件头已经改成说这件事。

**§7.2 `.persist` —— 上一版就已经确认用不了**（TS core 专属），手写那套继续留着。

**`store` / `sqlite` / `credentials` 三个 capability —— 一个都没开。**
理由同 §7.4：能力本身是真的，但把已经正确、已经被两个版本打磨过的存储换掉，
需要一次真机往返来确认，而这里没有。

### 顺带更正：噪声重测这件事本身，一开始是跑不完的

`test-analysis.mjs --record` 在 §2.5 之后有一段 multi-PV 扫描，要走过课程与
题库的全部局面 —— 而那里面有八个非法局面，Stockfish 19 遇到它们会 abort 整个
wasm 模块。于是这个脚本**自换引擎以来一次也没跑完过**，`docs/measured.json`
也就一直停在 Stockfish 18 的数字上。修掉那八个局面之后它才第一次跑通。

跑通之后的结论，三轮独立测量，**按轮配对读**（因为轮与轮之间的散布和效应一样
大，把三轮平均起来会把两者混成一团）：

| | `?` 120→200 | `??` 120→200 |
|---|---|---|
| 第一轮 | 60 → 73 % | 86 → 88 % |
| 第二轮 | 64 → 73 % | 82 → 84 % |
| 第三轮 | 58 → 64 % | 80 → 82 % |

三轮全部改善，两个标注都是。所以 **分析 的预算从 120 提到 200 毫秒**（精析仍
是 400）：`?` 是玩家会盯着某一手去看、去改的那个标注，而 120 毫秒下它跟自己
只对得上五次里的三次。代价是一趟棋谱库全库分析贵约 1.7 倍 —— 那一趟可以切到
后台、可以暂停续跑，玩家不会坐在那里等。

`?!` 在三轮里也都改善（40 → 47 % 左右），而且离 §5 定的 60 % 及格线仍然很远，
400 毫秒也救不回来 —— 这正是 7.0 把它默认收起来、而不是拿深度去买它的理由。

顺带一条不太好看的：**Stockfish 19 在同样的毫秒预算下比 18 更吵**。同一局面
两遍评估的中位抖动 8 → 9 厘兵、九分位 33 → 42 厘兵。这是 1 MB 网络用体积换来
的，`review.js` 的文件头已按实测改写。

### 另一条更正：题库门禁自己错了两遍，错的都是测量

值得单独记，因为教训不在结果里：

1. **按名次判，不按差距判。** 判据是「存的答案是不是引擎首选」，而打印的
   `gap` 是引擎前两名之间的差——从没量过「引擎最佳与存的答案」差多少。于是
   一厘兵之差和 262 厘兵之差被一视同仁地退役了 39 道。
2. **改成量差距之后，两轮仍然对不上。** 复核报出九万多厘兵的差距，那是杀棋
   分：这一轮引擎看见强制杀、上一轮没看见，同一局面、同样深度。根因是
   **脚本从来没在题与题之间清空置换表**，每道题继承前面所有题留下的哈希，
   于是 `go depth 18` 的结果取决于它前面搜过什么，也就取决于题目集、洗牌
   顺序、有没有删过题。

补上 `ucinewgame` 之后，同一份 60 道样本连跑两轮逐条完全一致。据此把题库
**恢复到未删减的 1023** 重判——按不可复现的数据做的删除不能当起点。

第一个可复现的结果：干净 833 · 已记下同等解 13 · 确实更差 21 · 未记下的同等解
27。退役 21 道（最小差 61 厘兵，六道是引擎有强制杀而存的答案够不到），题量
1023 → 1002。独立复核：`确实更差 0 · 未记下的同等解 0`，门禁通过。

三条可带走的：

* **一次删除的可信度，不会高于它背后那次测量。**
* `go depth 18` 看着像确定性的东西，只有置换表干净时才是。
* 跳过工具自己写明的复核步骤，等于把它的自我报告当成结论——这一轮反复三次，
  起点就是我跳过了那一步。

### 这一版没有做过的验证

和 6.0 / 6.1 一样，如实写在这里：

   「抄对的那些在真机上也对」。
3. **签名与公证仍未做**，首次打开仍要右键过 Gatekeeper。
4. `docs/manual-check.md` 新增的棋谱库条目**需要一次真机走查**才能打勾。

## 11 · 7.0 发布之后的复查

7.0 上线之后又过了一遍，重点放在这一版里最没被人看过的那部分代码——也就是
刚写出来的棋谱库本身。找到两个真缺陷，都在诊断这一条链路上，都已在本次修掉。
写在这里的每一个数字都是跑出来的，不是推出来的。

### 11.1 每手厘兵没有钳制到评估窗口——6.1 修过的那件事，抄漏了

`analyseLibraryGame` 写 `an.losses` 时是自己算的：

```js
return Math.max(0, (a - b) * mover);   // 7.0
```

`review.js` 的 `lossOf` 不是这样算的。它先把两端都拉进 ±`EVAL_WINDOW`（1000）
再相减，而这正是 6.1 专门修过的缺陷：一步快搜报「杀棋」、下一步只报「大优」，
两个标量差着九千多，照直相减就等于把「这条尺子能表达的最大失误」记在一个什么都
没做错的人头上。

棋局级的 ACPL 一直是安全的——它走 `lossesBySide` → `lossOf`。漏掉钳制的是
`an.losses` 这个数组，而**偏偏只有它会被 `foldGame` 折进分阶段 ACPL**，也就是
诊断页唯一真正给建议的那个数字。

拿 `library.js` 实跑出来的量级（20 局，每局 80 半着，三个阶段每手都恰好亏 30
厘兵，唯一的差别是其中 6 局的残局里有一手引擎报了杀）：

| 种子 | 开局 | 中局 | 残局 | `weakestPhase` |
|---|---|---|---|---|
| 没有报杀的那一手 | 30 | 30 | 30 | `null` |
| 20 局里 6 局有一手报杀 | 30 | 30 | **413** | **`end`** |

这个人在三个阶段下得一模一样，诊断却告诉他「该练残局」。而且这不是偶发：报杀
出现在残局的概率远高于开局，所以偏差是**系统性地偏向残局**的。

修法：`analyseLibraryGame` 改为直接调 `Review.lossOf`，不再自己算一遍。
另外，7.0 已经写进 localStorage 的那批记录同样是坏的，而且光把存下来的数字
截到 1000 并不能还原——「杀棋 5 步 → 杀棋 9 步」钳制后是 0、不钳制是 400。
`an.scalars` 就在记录里，所以正确的修法是开库时拿 scalars 重算一遍
（`rescoreLosses`，幂等，本版写出来的记录进出不变，因此不需要版本位）。

### 11.2 `foldGame` 完全没有读 `g.fen`——`[SetUp]` 局的每一手都记到了对手账上

`entryFrom` 会把 `[SetUp]`/`[FEN]` 局的起始局面存下来（7.0 做对了，e2e 也钉着
这一条），但 `foldGame` 里写死了两句：

```js
if ((i % 2 === 0 ? "w" : "b") !== side) continue;   // ply 0 一定是白方？
const moveNo = Math.floor(i / 2) + 1;               // 一定从第 1 手开始？
```

FEN 的第 2 段和第 6 段各自否定了其中一句。实跑的后果（20 局，FEN 说黑方先走、
从第 30 手开始，黑方每手亏 200、白方一手不亏）：

| | 开局 | 中局 | 残局 |
|---|---|---|---|
| 7.0 读出来 | 0 厘兵/手（240 半着） | 0 厘兵/手（160 半着） | 无数据 |
| 事实 | 无数据 | 200 厘兵/手（60 半着） | 200 厘兵/手（340 半着） |

也就是：**玩家自己的每一手都被算成了对手的**，剩下对手那些一手不亏的记在玩家
头上；再加上一个从第 30 手开始的局面被整个归进「开局」。`peak`（失误最密集的
回合）同样跟着错位。

修法：新增 `startOf(g)`，从 FEN 里读出 ply 0 是谁走的、第一手是第几手；手数规则
和 `review.js` 的 `moveNumber` 一致（「黑方先走的局从 `1…` 开局，白方的应手仍是
第 1 手」）。这是那条规则的第二份拷贝，是有意的——`library.js` 按设计不 import
任何东西，测试才能在裸上下文里跑它。

### 11.3 守卫

- `scripts/test-library.mjs`：`[SetUp]` 局的归属与阶段，三条断言。写第一版时
  断言本身写错了（把第 30–32 手当成了残局，`MIDDLE_UNTIL` 是 32），是测试错、
  代码对，已改断言。
- `scripts/test-library-e2e.mjs`：直接喂一份 7.0 形状的存档（`losses` 是没钳制
  的原始差值，`scalars` 在旁边），断言诊断页读出来的是 151 厘兵/手而不是 1270，
  并且整页不出现四位数的每手厘兵。

### 11.4 复查过、确认不是缺陷的

- `reclaimLibrary` 改名字之后不动 `an`——对的，那一趟分析量的是两边的每一手，
  换把椅子照样答得上。
- `an.acc` / `an.acpl`（棋局级）走的是 `lossesBySide`，一直有钳制。
- `tags` 走 `classifyByWinPct(winPctDrop(...))`，胜率函数在杀棋分附近本来就饱和，
  不受 11.1 影响——所以 `badRate` 和母题统计是对的，错的只有分阶段 ACPL。
- `app.zon` 里没有 `.updates` 段，`runner.zig` 的四个读取器因此一律回落到 null。
  这与 §10「没做到的」里记的一致，不是新缺陷。

### 11.5 版本号没有动

这一版的改动留在 7.0.0 上，没有改 `app.zon` / `build.zig.zon` / `package.json`。
发不发 7.0.1、什么时候发，是另一个决定。

### 11.6 §10 这张表本身漏掉的（7.1 补记）

7.1 动手前又把 §10 的两张表对着代码核了一遍，发现表本身有洞。6.0 的教训原话
是「计划里打了勾而代码里没有的东西，会在下一版被当成『已有』继续往上盖」——
下面两条比那还糟：一条连勾都没打，所以两张表里都查不到它。

**§6.3「错题自炼扩容到真实规模」——既不在「做到了」，也不在「没做到的」。**
它确实没做：`Mistakes.addMines` 在 7.0 里只有两处调用，都在棋盘那条路上，
`runLibraryPass` 一次也没调过。§9 早就写着「§6.3 跟着 §6.1 走，否则第一次
批量导入就会冲掉老错题」，而 7.0 做了 §6.1 没做 §6.3——风险之所以没爆，只是
因为库根本没接进错题本。7.1 补上（v7-1-plan §1.2）。

**§6.4 打了勾，但它自己写的验收没做。** §6.4 的验收原话是「在 28 局语料上，
能给出解释的失误比例要量出来并写明；抽样人工核对解释的正确率，低于某个门槛
就默认关掉这个功能并如实记录」。`docs/measured.json` 里没有这个键。功能确实
实现了（母题取的是引擎在你走错之前那一手），**但「量出来并写明」这一半一个
字都没有**。7.1 补测（v7-1-plan §3.1）。

**外加一条 §10 说做到了、代码里却是死的。** §6.2 的「按开局的战绩与失分点」
记在「做到了」那一行里。`diagnose()` 确实有这套算术，`foldGame` 确实读
`g.eco`——**但 7.0 里没有任何一处给条目写过 `eco`**，所以 `d.ecos` 永远是空
数组，「开局战绩」那一段从来没有渲染过一次。e2e 之所以没抓到，是因为它把
`eco: "B20"` 手工塞进了种子数据：测试测的是 `diagnose()` 的算术，而没有人测
过「应用会不会产出这个字段」。7.1 补上 `fillOpenings()`，并且这一次由 e2e
从真实的着法里读出 C60 来断言。

三条放在一起的教训是同一条：**把「算得对」和「有人把数据喂进来」当成一件事，
是这三个洞共同的成因。** 种子数据写得越顺手，这个洞越难发现。

### 11.7 换引擎漏掉的第三处标定（7.1.1 补记）

7.0 换掉引擎（Stockfish 18 → 19 lite-single）之后，有三处标定失效。§10 抓到
两处并写了进去：噪声重测（`scanNoise`）和题库门禁。第三处是
`measured.json` 的 **`noviceScore`** —— 削弱档对「只会不一步送子的随机机器人」
的得分率，最后一次记录是 **2026-07-31**，也就是换引擎之前。没有人重测。

它是在 **v7.1.0 的发布门禁上炸出来的**：`careful` 对 beginner 档得分率 78%，
区间 35–75%，发布在打 tag 之前就停住了（tag、构建、publish 全部 skipped，
没有发出任何东西）。

**先排除了是 7.1 的改动**：参与这次测量的四个文件（`test-novice.mjs`、
`engine.js`、`chess.js`、Stockfish 胶水）在 7.0.0 和 7.1 之间逐字节相同。

SF19 下重测（各 5 轮 × 20 盘，共 100 盘）：

| 档 | 旧记录（SF18） | 实测（SF19） | 一场 20 盘的 σ |
|---|---|---|---|
| beginner · careful | 56% | **59%** | **7.7** |
| casual · careful | 27% | **29%** | **10.1** |

两档都向上漂了约 3 点，方向与「SF19 lite-single 更弱」一致。

**但漂移不是这次红的主因，缺离散度才是。** 旧区间 35–75 是从单个数字「推」
出来的宽度——记录里从来没有标准差这一项。59 ± 3σ 应当是 35–83，而旧上界 75
只在真实均值上方不到 2σ，于是这条门禁本来就会每六七次红一次。九次观测里最高
78，正落在 75 与 83 之间：**v7.1.0 是被门禁自己的噪声拦下来的，不是产品出了
问题。**

修法三条，一条比一条根本：

1. `test-novice.mjs` 补 `--repeat=N`，把整场比赛重复若干轮，记录每轮得分与
   样本标准差。区间宽度从此有测量支撑，不是估的。
2. 两档区间改为实测均值 ±3σ（beginner 35–83、casual 0–60）。casual 的下界是
   0 且**不构成门禁**：29 − 3σ 已经低于零，20 盘的样本分辨不了，如实写在
   源码注释里。发布路径跑的是 beginner 档，那一档两边都是实的。
3. **`scripts/test-chess.mjs` 新增守卫：区间必须等于记录里的均值 ±3σ。**
   这是这个仓库原本缺的那一环 —— 原有守卫只比对「README 和 engine.js 是否
   引了同一份数」，两边一起过期它就一起放过，而没有任何东西把「引擎换了」
   连到「这份标定已经是小说了」。现在重测过却没改区间会当场红。
   （写这条守卫时它立刻抓到我自己把 ±3σ 取整算错了：35–83 写成了 36–82。）

顺带修掉守卫自己的一个老毛病：它的正则把盘数写死成 `/32 盘对新手得分率/`，
盘数一改就匹配不上，报的是「README 不再写这个数」而不是它该报的那个不一致。
**把被检查的数字写进检查它的正则，等于给守卫设了有效期。**

README 与 `engine.js` 注释里的 56%/27%/32 盘同样是 SF18 时代的数，一并改正。
