# 7.2 · 把 7.1 接通的那条链路做扎实，再给它一个新的上游

写在 7.1.1 发布之后、动手之前。规矩和前几版一样：每条说清楚**依据是什么**，
依据是核过的代码或跑出来的数；每条有**验收**；发布前补**落地记录**，做到的和
没做到的都逐条写。

---

## 0 · 这一版要解决的问题

7.1 做的是接线：棋谱库的产出终于流向棋盘、错题本、日课和进步页。接完之后再核
一遍，发现**接通了，但接出来的东西质量没人管**——两条都是 7.1 自己留下的债。

### 债一：库里挖出来的错题，答案有相当比例是错的，而且永远修不了

`library.js` 的 `pending()` 是这样定义的：

```js
return (list || []).filter((g) => g && !g.an && g.plies > 0)
```

**一局分析过一次就再也不会被重新分析。** 而库用的是 200 毫秒快扫
（`LIB_BUDGET = SCAN_BUDGET`），`docs/measured.json` 的 `mineRevision` 量过同
一件事在 120 毫秒上的后果：

| | |
|---|---|
| 快扫预算 | 120 ms |
| 精析预算 | 400 ms |
| 精析**撤销**的 `??` | **40%** |
| 剩下的里精析**改了最佳着法**的 | **33%** |

7.1 之前这不要紧：错题只来自棋盘，而棋盘上跑一次「精析」就会走
`reviseMines` 把它们修正。7.1 之后，**上限 90 道的错题本主要来源变成了库**，
而库这条路上没有任何加深的入口。200 毫秒的撤销率低于 120 毫秒的 40%，但
**没有量过**——只知道不是零。

### 债二：错题不知道自己是从哪一局来的

`drillFrom` 返回的全部字段：

```
id / cat / fen / solution / played / loss / ply / rev / side
```

**没有任何指回源局的引用**，棋盘那条路也没有。于是 7.1 开的门是单向的：库 →
棋盘、库 → 错题，但你在做错题时再次做错，问不出「这是我哪一局」。而那个上下文
正是让它记得住的东西——`mistakes.js` 的文件头讲的就是这件事。

### 然后才是新东西

`docs/v7-plan.md` §8 记了三条「下一版之后」。其中**只有开局库训练因为 7.1 而
升值了**：它原本的卖点「显示覆盖缺口」只是一句列表差集，而 7.1 的
`fillOpenings()` 补上之后，`diagnose()` 的 `ecos` 里有了真实战绩，那句话可以
变成「你对它没有准备 —— 而你在它下过 14 局，输了 9 局」。

## 1 · A1：库里的局可以再深分析一遍

**做什么**：库列表给每一局一个「再深一遍」的入口，用 400 毫秒重跑，走现成的
`reviseMines` —— 那个函数本来就是为这件事写的（5.1，audit F2），只是库这条路
从来没调用过它的修正语义。重分析后 `an.budget` 记录新预算，`pending()` 不变
（它管的是「没分析过」），新增的是一条按预算判断的「值得加深」列表。

**为什么不是默认全用 400**：一局 80 手，200 毫秒是 16 秒，400 毫秒是 32 秒。
两百局就是 53 分钟对 107 分钟。默认预算不动，加深是按需的。

**验收**：
- 量出 200 → 400 的撤销率与改答率，和 `mineRevision` 同一套方法，写进
  `docs/measured.json`（新键 `libRevision`，或并进 `mineRevision`）。**这个数
  没量出来之前，这一条不算做完** —— 7.1.1 刚教过一次「推出来的数字会过期」。
- e2e：一局已分析的棋点「再深一遍」，`an.budget` 从 200 变成 400，而且它铸的
  错题走了 `reviseMines`（撤销的题从错题本消失、改答的题答案变了）。

## 2 · A2：错题指回它的来源局

**做什么**：drill 上加来源字段，记住它是从哪一局的第几手来的。两条路都填：库
的分析趟填库局 id，棋盘的分析趟填战绩记录 id（`store.game.recordedId`，它已经
存在）。做题页给一个「看那局棋」的入口，按来源跳到库列表或对局历史并载入那局，
落到那一手。

**边界**：来源局可能已经被淘汰（库满 500 / 战绩被清），所以入口只在来源还在时
出现 —— 这一页一贯的 P3 规矩。

**验收**：单测钉住「两条路都带来源、来源不在时入口不出现」；e2e 从一道库来的
错题点进去，棋盘上是那一局、游标停在那一手。

## 3 · P1：开局库训练（本版 headline）

**做什么**：
1. **导入自己的开局体系**：一份 PGN（带变着）进来，用 `pgn-parser` 解析、
   `game-tree` 建树，存成一本「我的开局书」。白黑各一本，因为同一个人执白执黑
   的体系是两套。
2. **背它**：用现成的 `srs.js` 排期。一道题 = 书上的一个分支点：给你局面，你
   要走出书上的那一手。走偏了当场告诉你书上走什么，并且可以从那里继续。
3. **覆盖缺口，用真实战绩说话**：把书的根部展开和 `diagnose()` 的 `ecos` 对
   起来 —— 你下过但书里没有的开局，按你在它上面的战绩排序。

**为什么现在做**：零件全都在（`pgn-parser` / `game-tree` / `srs` /
`opening-tree` / 库的 ECO 统计），是纯组合。而缺口那一半**只有 7.1 之后才成
立**：7.1 之前应用不知道你在哪些开局里真的输过。

**明确不做**：不替换现有的 195 条内置开局书和它的做题轨道。那本书是「教你
开局原理」，这本是「背你自己的体系」，两件事。

**验收**：
- 纯模型层单测：建树、分支点枚举、按 SRS 排期、缺口计算（书里没有 × 库里下过）。
- e2e：导入一份带变着的 PGN，出现分支点题；走错给出书上的着法；缺口那一段引到
  真实战绩。

## 4 · P2：app.js 拆出棋谱库界面

`app.js` 现在 **10161 行**（7.0 是 9466，7.1 加到这里），其中棋谱库那一块是
**1026 行**（5010–6036）。`docs/refactor-plan.md` 的 P0–P6 全部结案，没有任何
计划在管这件事。

棋谱库是最干净的拆分对象：纯模型已经在 `library.js`，app.js 里剩的是调度、
持久化和两个界面。抽成独立模块，app.js 回到九千行出头。

**验收**：拆完行为不变 —— 现有的 library e2e 七组一条不改地全过。
