# 重构计划

目标：让产品达到「极其优雅和精致」，且让这种状态由结构保证，而不是靠每次改动时的自律维持。

先读 [`design-constraints.md`](./design-constraints.md)。它是不可回退的既有判断 + 已核实的 33 条缺陷清单，本文件只安排顺序。

代码基线：`main @ 8b66289b5171`。

---

## 总判断

这是一个**纯函数层写得比多数商业产品好、编排层与表现层欠一次整理**的仓库。

不动的部分（约 115 KB）：`chess.js` · `fide.js` · `review.js` 的算术 · `srs.js` · `material.js` · `pgn.js` · `editor.js` · `drills.js` · `opening-coach.js` · `persona.js` · `engine.js` 的并发编排 · `host.js`。这些有清晰边界、纯函数、单测，以及把实测写进注释的习惯。72 课的编排与文字纪律同样站得住。

重构面（约 310 KB）：`app.js`（5 282 行 / 221 函数 / 56 个模块级 let / 65 处 `sync()` / 211 次 getElementById）· `index.html`（36 KB，114 button，7 模态框）· `styles.css`（1 395 行，276 规则，注释占 28%）。

五轮 review 查出的问题几乎全部落在三类：

1. **同一件事被写了两遍** —— 准确率公式、强度实测数字、Esc 名单、i18n 重复键、失误色三份
2. **一个已经准备好的信号没人接** —— `storageSet()` 的返回值、`lang` 属性已设却无 `:lang()` 规则、`drillOutcome()` 是纯函数却只报结果
3. **一个刻度从没被收敛过** —— 棋盘的半径与线宽、四主题的标记强度、难度分档

都不是能力问题，是**没有唯一来源**的问题。所以整个计划可以压成一句话：*给每一件事一个唯一的出处* —— 状态归 store、样式归 token、文案归语义键、数字归一个公式、实测归一份 JSON、脚手架归仓库。

## ⚠ P-1 · 先回答这个问题（阻塞一切）· **已结案**

原始判断是：README 与 `.github/workflows/checks.yml` 指名的 `scripts/*.mjs`、`src/main.zig`、
`src/runner.zig`、`app.zon`、`build.zig`、`package.json` 都不在仓库里，CI 每次 push 都在跑不存在的文件。

**核实结果：这个前提不成立。** 除 `package.json` 外全部文件都在 `main @ 8b66289` 里：

| 声称缺失 | 实际 |
|---|---|
| `scripts/*.mjs` 15 个 | **17 个**都在（`git ls-files '*.mjs'` = 17）；`scripts/` 下另有 `package.sh` |
| `src/main.zig` · `src/runner.zig` | 都在 |
| `app.zon` · `build.zig` | 都在（版本 1.25.0，两处一致） |
| `package.json` | **确实缺失** —— 唯一真实的那一条 |

原文「全仓库 84 个文件里 `.mjs` 数量为 0」是对一份不完整检出的统计：实际 `git ls-files` 为 109 个文件。

按处理方式 **A** 结案。所做的事只有一件：补上缺失的 `package.json`，让 README 与验收标准里的
`npm test` 真的是一条命令。脚本分三组，因为它们的代价差三个数量级：

- `npm run test:static` —— 单测 + scope-check + manifest-check，秒级，无外部依赖
  （P0 之后 scope-check 退役，见下）
- `npm run test:e2e` —— 六个浏览器 E2E，需要 Playwright（没有则各自打印「跳过」并通过）
- `npm run test:engine` —— 开局/战术/新手档/强度实测，要跑引擎，分钟级，**不进 `npm test`**

`npm test` = static + e2e，与 `.github/workflows/checks.yml` 的两个 job 一一对应。

**基线核实**：改动前全部 9 个检查在本机绿（`test-chess` / `scope-check` / `manifest-check` +
六个 E2E，Chromium）。护栏是在的，P0 可以开始。

## P3 · 界面重制（3–4 周 · 用户可见的那一次改版）· **已完成**

原则：**按时态组织，不按功能罗列。屏幕上的每个控件此刻都可用。**

> ### 开工前先读这一段
>
> **1、4、6 是一个改动，不是三个。** 这是排期时没看出来的耦合，动手前值得知道：
>
> - **3.1** 要把模式行提到应用级，最自然的位置是顶栏；
> - 但顶栏 44px 里已经塞了五种语义（品牌、状态胶囊、无标签的 `14/14`、四个动作、☰），
>   **3.4** 正是要卸掉其中两种 —— 所以 3.1 的落点由 3.4 腾出来；
> - 而 3.4 要拿掉的「教学任务全文」并不是冗余：`statusText()` 只在**面板收起时**
>   才把整句任务塞进胶囊（`max-width:44vw` + 省略号），面板开着时它显示课名。
>   那是给收起状态用的兜底 —— 而 **3.6**（面板收起后保留谁走 · 时钟 · 上一手 ·
>   子力差）正是它该去的地方。
>
> 所以最小的自洽单元是 **3.1 + 3.4 + 3.6 一起做**。单做 3.1 会撑破顶栏；单做 3.4
> 会让收起面板的教学模式丢掉唯一的任务提示。
>
> 顶栏改完的目标形状：
> `[模式分段] [状态胶囊——只说谁走] …… [本时态的动作] [☰]`
> —— `14/14` 回面板（它是复盘/课程的位置指示，不是应用级信息），品牌字标可以
> 只留标记或整个去掉（这是有原生标题栏的桌面应用）。
>
> **3.3 是验收标准的核心**，也最好验：「任一时刻可见的禁用控件数为 0」可以直接
> 写成一条浏览器断言，对四种时态各跑一遍（0 手 / 进行中 / 已结束 / 教学）。
>
> **3.7 与其余六项无耦合**，可以单独先做：四个不可撤销的动作（清除存档、教学重置、
> 统计清零、认输）现在在四个位置、三种叫法，且都是常驻家具。
>
> ### 为什么停在这里
>
> P-1 到 P2 的每一项都能由测试判定对错 —— 行为、数值、结构。**P3 是「用户可见的
> 那一次改版」，而它的对错很大一部分只有看着屏幕才判得了。** 现有的浏览器检查能
> 回答「有没有抛异常」「元素在不在」「按钮等不等宽」，答不了「这一版好不好看、
> 好不好用」。在没人看得见结果的情况下盲改版面，风险不在测试会不会红，而在测试
> 全绿而产品变难用 —— 这正是这份计划最不想要的那种改动。

1. ✅ 导航压两层：模式提升为应用级切换，面板内只留视图分区。（现状 284px 里叠三层，前两层刻意共用同一套下划线语汇 —— 统一语汇解决了「学两次选中态」，代价是两条长得一样的行，一条含义是换产品，一条是换视图。）

## 工期与风险

单人推进约 **8–13 周**。P0–P2 六周是不改行为的地基，真正的改版风险集中在 P3。规则、引擎、内容三块不动，回归面只有界面。

**最大的风险不是技术，是丢掉已有判断。** 这套代码的注释里记着大量实测结论（注释占 styles.css 全文 28%，88 块 16.7 KB），它们是这个仓库最值钱的东西之一，但没有任何机制保证还成立 —— 缺陷 11 就是注释比代码旧造成的死代码。`design-constraints.md` 是为此存在的：**动它之前先读它。**

## 顺序为什么不能换

- 没有 P-1 的护栏，任何阶段都无法验收。
- 没有 P0 的模块边界，P1 的 store 会变成第二个 `app.js`。
- 没有 P1 的受控渲染，P3 的界面重制会重现同样的手工同步。
- 没有 P2 的 token 层，P4 的精致度调整会变成又一轮硬编码。
