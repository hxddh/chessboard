# 19.0.0 全面评估 · 下一个大版本（21.0）建议

写于 2026-11-08，基于 main @ 2d3761f。这个提交和 19.0.0（1fbbf83）逐字节相同，20.0.0 已经整体回退。

**已定（2026-11-08，「按建议来」）**：第 6 节每一条都取推荐项，见第 6 节末尾的「已定」。先做 19.1（第 5 节 F 组，计划与落地记录见 [v19-1-plan.md](v19-1-plan.md)），21.0 的计划之后按惯例拆成 `docs/v21-0-plan.md`（依据 / 做什么 / 验收 / 落地记录）。

**版本号**：GitHub 上 v20.0.0 的 tag 和 release 还在，所以下一个大版本建议叫 **21.0**，避免 tag 冲突，也避免让人以为是 20.0 换了个号重发。

## 0 · 结论先行

| 方面 | 评分 | 一句话 |
|---|---|---|
| 规则与对弈正确性 | ★★★★★ | chess.js 加 FIDE 判和补丁；21 档对手的分数是用循环赛实测拟合的，不是拍脑袋 |
| 速度 | ★★★★★ | 首帧 56–96 ms，对手应着约 0.5 s，20–36 步的复盘 4–8 s |
| 视觉与三语文案 | ★★★★☆ | 干净、有层次；1376 个界面键三语齐备，中英日都不截断 |
| 教学闭环 | ★★★☆☆ | 单步反馈已经是顶级水平，但课、题、局、复盘之间没有连起来（见第 2 节） |
| 前端架构 | ★★☆☆☆ | 能用，测试也守得住，但扩展成本高（见第 3 节） |
| 原生壳与发布 | ★★☆☆☆ | 桥接安全、CSP 都做对了；没签名、没公证、没自动更新，真机验证不挡发布 |
| 测试与 CI | ★★★★☆（浏览器）/ ★★☆☆☆（真机） | 浏览器一侧有几千条断言，非常扎实；真 WebView 一侧几乎是盲区。20.0 就栽在这里 |
| 发布节奏 | ★★☆☆☆ | 4 周发了 12 个大版本（9.0–20.0），其中 1 个回退 |

**三个核心判断**：

1. **19.0 的底子是好的。** 单步反馈（谜题的反驳、再试一次时说后果、残局丢胜当场停、自己的错第二天变成题）和对手的拟真度，都已经是同类产品里的上游水平。下一版不需要推倒重来。
2. **20.0 失败的直接原因不是方向错，而是两点：**
   - **一次性换掉了所有东西**：界面层、存储、引擎服务、SDK 版本、打包目标、存档全部同时换；
   - **真机验证不挡发布**：`docs/manual-check.md` 写着「没人走过的步骤不挡发布」。

   20.0 计划里的问题诊断，这次在 19.0 上逐条复核，**大部分仍然成立**（第 2 节）。所以 21.0 应该做 20.0 想做的事，但**换一种做法：先建立真机门禁，再逐块替换，每一步都能单独发布**。
3. **下一个大版本的主题建议定为「可信」**：
   - 装上一定能用：真机门禁、签名、自动更新；
   - 教的每一句话都对、都有用：教学闭环的缺口补上；
   - 改起来不再怕：渐进重构。

   不加新页面，不改存档格式（不破坏兼容）。

## 2 · 产品与教学

### 2.1 已经是顶级、下一版不要碰的

- **谜题的反驳**：「还不是将死 —— 黑方可走 Kh8」。
- **再试一次第一次走错说后果**：「a3 之后，对方可以走 Bxe3+」。
- **残局丢胜当场停**：「关键格」里走 2.d4，立即提示「这一步把胜局走成了和棋」，并复述要领。
- **自己的错变成第二天的题**：今天页显示「先清复习 3 题 · 今天那局第 8 步的失误」；复盘总结连到具体的一课。
- **名局猜着**：按胜率差打分。
- **低档对手像人**（19.0 T5）；**速度**；**视觉语言**。

### 2.2 20.0 计划列的问题，在 19.0 上逐条复核

| 问题 | 19.0 上的结论 | 证据 |
|---|---|---|
| 课程不看定级 | **仍存在** | 定级 1675 后，今天页仍是「继续 · 第 1 课」，「我的」页下一枚成就是「完成第 1 课」 |
| 好几个等级分 | **仍存在，而且不止 4 个** | 谜题 760/800、「这一类」1460、对局 811（暂定）、「近期表现分 132」；「我的」页反而不显示对局分 |

| 复盘的「再试一次」埋得深 | **仍存在** | 1440×900 下按钮压在屏幕下沿（875–907 px）；1024×700 下整张卡片在首屏外 |

### 2.3 这次新发现的问题

1. **再试一次被剧透**：关键时刻卡片默认就写着「更好的是 Bxd4…」，重试的输入框就在它下面。19.0 T1「先让你想」的效果因此打了折扣。
2. **完整报告自相矛盾**：总结写「白方 · 只有一次严重失误」，同一张表里白方的严重失误是 2。两盘走查都出现。
3. **失误分级只看胜率**：已经落后时白送后只记 `?`，送车（20.Rd3）不算失误。俱乐部棋手最该学的那一步被漏掉了。
4. **对局里提示一按就是答案**：「提示 · Nf3」加箭头。谜题已经分两步给提示，对局还没有。
5. **重复太密**：新手 5 分钟里见到同一个 Ra8# 局面 3 次（第 7 课一次、谜题第 1 题一次、错了之后「先清复习」立刻又排一次）。
6. **课程走错只复述题目**：第 18 课走 Nd6，提示仍是「找一个能同时攻到…的马位」。第 18 课题面还写着「e8 车」，第 7 课写着「把后走到 g7」。19.0 T4「题面不写坐标」没有做干净。
7. **定级结束没有结果页**：做完第 6 题直接跳进普通谜题，不说你多少分、配了哪位对手。
8. **今天页小毛病**：
   - 「课」一栏显示 14，没有目标（旁边是 2/5、1/1）；
   - 「继续」里列着没开始过的残局和名局；
   - 刚下完一盘，开局浏览器仍显示「棋谱库是空的」。

### 2.4 与顶级产品的差距

| 产品 | 它做对的、我们还没做到的 |
|---|---|
| Chess.com | Game Review 的 Retry 是首屏主按钮、不剧透；对外只有一个主等级分 |
| Lichess | 「从错误中学」先提示后给答案；对局提醒在你确认落子之前 |
| ChessKid | 课程按水平跳过；每个概念练好几个局面；有闯关地图 |
| Chessable | 按内容排间隔复习，同一题当天不会马上重复 |

## 3 · 前端架构与代码

### 3.1 现状数据

20.0 计划里的说法，这次逐条核对。只统计纳入 git 的源码：192 个文件，64,432 行。

| 指标 | 19.0 实测 |
|---|---|
| `index.html` 里写死的 id | 472 个 |
| 直接 `getElementById` | 41 个文件里共 397 处，另有约 210 处走封装函数 |
| `createX` 工厂 | 60 个。依赖最多的几个：`createPuzzlesUI` 61 个键、`createGameController` 47、`createLessonsUI` 42、`createIO` 41 |
| 全局可写状态字段 | 111 个（game 24 + session 40 + ui 47）。`app.js` 里 190 处直接写，`game-controller` 33 处 |
| 棋盘 | 模块级单例（`board.js` 里的 `_canvas`、`_model`、`_anim`） |
| 存档层数 | localStorage、原生文件（A/B）、IndexedDB（68 片），三层按 `writtenAt` 对账 |
| 160 个半回合的自动存档总写入 | **3.17 MB**：每步都把整棵树写一遍，O(n²)；最后一次单次 37 KB |
| `app.js` | 4,777 行 |

**好的一面**：
- `innerHTML` 赋值为 0 处。PGN 的头部、注释和同步来的数据全部走 `textContent`，没有 XSS 路径。
- CSP 严格：`script-src 'self' 'wasm-unsafe-eval'`、`object-src 'none'`、`base-uri 'none'`。
- Stockfish worker 的出错、卡死都有带代数（gen）的清理，旧 worker 迟到的回复会被丢弃。
- 三语的键是否齐全，由测试强制检查。

### 3.2 确认的缺陷

| # | 严重度 | 位置 | 问题 | 证据 |
|---|---|---|---|---|
| D1 | **P1** | `src/web/js/persist.js:641` | 从原生文件恢复时，如果写 localStorage 失败（比如配额满），这里直接 `return "corrupt"`，前后两个同类分支都会先 `blockMirror()`，这里没有。随后 `finally` 里的 `markAllDirty()` 加上放开的镜像，会把没恢复进来的键从原生 manifest 里删掉。**结果是原生存档丢数据**，用户看到的提示还是「文件损坏」，和真实原因不符 | 用 `test-persist.mjs` 同款假 host 复现：manifest 只剩 `save`、`panelOpen` 两个键 |
| D2 | P2 | `src/web/js/human/worker.js:84` | Maia worker 的 `onerror` 只 reject 排队中的请求，不重置 `worker / booting / loaded`。之后每一步都发给死掉的 worker，各等满 4 s 超时。init 超时也不 terminate 旧 worker | 读代码确认 |
| D3 | P2 | `engine.js:403`、`engine.js:926`、`human/worker.js:75` | `createObjectURL` 从不 revoke。后台分析 lane 空闲 30 s 就关，下次再起，每次漏一份 worker 源码 blob | 全仓 `revokeObjectURL` 为 0 处 |
| D4 | P2 | `app.js:946/950`，`persist.js:427–497` | 每次自动存档把整棵树 `JSON.stringify` 两遍，每 400 ms 一次镜像 flush，每次至少 4 次桥接往返加 base64 | 即上表的 3.17 MB |
| D5 | P2 | 复盘总结 | 「只有一次严重失误」和表格里的计数对不上 | 走查截图 |
| D6 | P3 | 待核实 | `rep-db.js:58` 收到 `versionchange` 关库后没有重开路径；`fit-row.js` 先写后读布局；`mini-board.js` 的 ResizeObserver 从不 unobserve；`writtenAt` 用墙钟，系统时钟回拨时可能判反 | — |

### 3.3 为什么不再整体重写

20.0 想一次解决上面所有结构问题，结果是：
- 631 个文件，+37k / −126k 行；
- 同时换了打包目标（`safari15` → `es2022`）、CSS（没加 `@supports` 保护的 `color-mix`，要 Safari 16.2 以上）、module Worker、SDK 版本和存档。

这样一来，真机上任何一处不兼容都没法定位，只能整体回退。

**21.0 的原则**：
- 每次只换一层；
- 换下来的那一层有测试守着；
- 每一步都能单独发布；
- 每一步都在真机门禁下过一遍。

## 4 · 原生壳、发布与 20.0 复盘

### 4.1 19.0 做对了的

- **桥接面**：SDK 内建命令 7 个、应用命令 16 个，manifest-check 把页面实际调用和原生放行做双向校验。
- **文件路径**：只由原生侧签发（拖放、系统打开文件）；对话框在原生侧运行，路径不回传页面。
- **开发源只在 Debug 下信任**；WebView2 用户数据目录在 exe 目录不可写时退到 `%LOCALAPPDATA%`。

### 4.2 确认的问题

1. **没签名、没公证**：macOS 只有 ad-hoc 签名（`build-macos.yml:114`），Windows 没签名。
   - README 还在教「首次右键打开」，而 macOS 15 起这一招对未签名应用已经不管用，要到系统设置里点「仍要打开」。
   - 只出 arm64 包，Intel Mac 用不了。
2. **没有自动更新**：`chess.checkUpdate` 只查 GitHub 最新 release、给一个链接。SDK 自带的签名更新器没有接入。
3. **页面 JS 的错误不进原生日志**：只给用户弹提示（`notices.js:149`），真机上出了问题没有痕迹可查。
4. ~~发布版仍然响应自检环境变量~~：**19.1 核对后撤回。** 这是有意的设计：构建工作流的 selftest 步骤就是在要发布的那个 exe 上跑 `CHESS_SELFTEST=1`（见 `bridge.zig` 里 `seamsOpen` 上方的注释）；改写入路径的前提是能控制进程的环境变量，那时已经能执行任意代码。不改。
5. ~~Windows「可移动卷」判断有漏洞~~：**19.1 核对后撤回。** 盘符不同的路径（`bridge.zig:842`）随后还要过 `SYSTEM_COMPONENTS` 检查（`bridge.zig:813–830`），`C:\Windows`、`Program Files`、`ProgramData`、`AppData` 都会被拒；而且只有拖放和系统打开事件能签发路径。符号链接不解析这一点仍然成立，但可利用性很低，不改。
6. **SDK 分叉负担**：钉在 0.10.1，登记了 31 组、177 块差异，几组标着 lag。20.0 已经在 0.11.0 上验证通过，回退后又回到了 0.10.1。
7. **供应链**：
   - Actions 只钉主版本标签（`@v7`），没有钉 SHA；
   - SDK CLI 用 `npm i -g` 安装，没有哈希校验；
   - 发布件没有 SHA256 校验和；
   - 构建作业用 `windows-latest`，没有固定镜像版本。
8. **没有检测 WebView2 运行时**：缺了不会引导用户安装。
9. **原生构建只在发布时跑**：PR 上看不到原生结果。

### 4.3 20.0 为什么 CI 全绿、真机却坏了

没有找到正式的事故复盘（#130 说会补，还没补）。下面是这次审查找到的**确认的检测盲区**，以及**推测**。

**确认的盲区**：
- **原生自检只检查元素存在，不看画面**：「棋盘已画好」等于一个 performance mark 加上存在 canvas 元素。真 WebView 里从来没截过一张图，CSS 有没有加载、元素看不看得见都不检查。
- **视觉基线只有 Linux 无头 Chromium**，WebKit 上跳过。WebKitGTK 也不等于 WKWebView。
- **兼容目标被悄悄抬高**：19.0 打包目标是 `safari15`，因为最低系统 macOS 11 自带 Safari 14；20.0 改成了 `es2022`、未加保护的 `color-mix`、module Worker。CI 用的是 macos-26、windows-2025，也就是最新的 WebKit 和 WebView2，碰不到老系统。
- **每个场景都从全新的空 profile 开始**：没测过从 19.0 升级上来，带着旧的 appdata、WebView 存储和窗口状态启动的情况。
- **自检绕过了首次启动的「学」页**，直接跳到 `/play`。
- **20.0 没有全局 `error` / `unhandledrejection` 处理**。
- **真机走查一再标为「未做」，PR 照样合并发布**。

**推测**：
- 真机 Retina（dpr 2）与 CI 虚拟机（dpr 1）下 canvas 尺寸、布局不同；
- 从网上下载的 zip 带 quarantine 属性，ad-hoc 签名的 Stockfish 子进程可能被 Gatekeeper 拦截；
- 19.0 留下的窗口状态与 20.0 的新外观冲突。

**教训**：问题不在测试少，而在测试测的是「代码以为发生了什么」，不是「用户看见了什么」。

## 5 · 21.0 · 可信：装上就能用，教的每句话都对，改起来不怕

**要求**：
- 不加新页面；
- 不破坏 19.0 存档（照旧只往前迁移）；

### R · 渐进重构（strangler，每步可单独发）

按这个顺序，前一步的测试守住后一步：

5. **状态写入收口**：`app.js` 以外的写入改走 commit 辅助函数；开发构建用 Proxy 抓「没走 commit 的写入」。
6. **棋盘去单例**：改成 `createBoardView(canvas)`，`ChessBoardView` 留作默认实例的兼容层。
