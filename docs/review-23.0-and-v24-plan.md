**三个核心判断**：

1. **先发一个 23.0.1。** 23.0 把系统「打开」送来的文件也放进了拖放的路径规则，结果 iCloud Drive、邮件附件、`C:\chess\`、在资源管理器里双击 zip 里的 .pgn **都会被悄悄丢掉**：应用被拉到前台，什么也没打开。这是 23.0 自己带进来的回归，不能等两周。
2. **24.0 的主题建议定为「说对」：屏上的每一句话、每一个数都和事实一致。** 这次走查最常见的毛病已经不是「东西摆在哪」，而是「说的不对」：看了答案还写「解出！」、提示说「先用将军」而答案是吃子、复盘里 4 / 3 / 1 三个失着数、水平数三处三个说法、认输时胜率 95% 却掉 210 分。这些是教学产品最伤信任的地方。
3. **慢下来。** 22.0 评估就定过「一个大版本至少两周」，实际两周发了 8 个。每一版的 CI 都是绿的，但真机核对清单（`docs/manual-check.md`）从 21.0 起没有人走过，23.0 的两个安全问题（2.1、2.2）都是真机一走就能发现的。

### 2.2 · Windows 发布件仍能打开 DevTools

SDK 0.11.1 的 `webview_inspection` 只在 macOS 主机里接了线（`appkit_host.m`）。Windows 主机 `src/platform/windows/webview2_host.cpp` **从不碰 `ICoreWebView2Settings`**（本次在 0.11.1 的源码里 grep 过 `AreDevToolsEnabled` / `Settings`：没有），WebView2 的默认值是 DevTools 开、默认右键菜单开。所以 Windows 版按 F12 或 Ctrl+Shift+I 就能打开 DevTools，页面和存档照样能改；23.0 的发布说明写的是「macOS 版不能再被检查」，这句话本身没错，但只说了一半。

可选的修法（要 owner 定，见 6-2）：
- **a**：给上游提 issue / PR：`webview_inspection` 在 WebView2 上设 `put_AreDevToolsEnabled(FALSE)`。干净，但时间不由我们定。
- **b**：在我们的构建里编译一份打过补丁的 `webview2_host.cpp`（`build.zig` 已经在编译这个文件，只是路径指向 SDK）。登记进 `sdk-fork.json`，和 runner / build 一样由 `sdk-diff` 盯着。立刻能修，代价是第四份手抄文件。
- **c**：两个都做：先 b，上游合并后删掉。（推荐）

### 2.3 · 核对过、没有问题的

- 打包的 exe 确实不可检查：`zig build package` 的 runner 模块按 `package_optimize`（默认 ReleaseFast）编，`webview_inspection` 为 null → false；两个工作流和 `package.sh` 都是 ReleaseFast。
- `sync.zig` 的 `.unhandled`：Zig 0.16 的 `receiveHead` 直接把 3xx 交回来，映射成 `http_3xx` 错误。唯一要记住的：GitHub `releases/latest` 在仓库改名后会回 301，届时更新检查会报错。
- `stripResult` 现在只认独立的结果 token，只用在 chess.js `pgn()` 的输出上，那里总有空格，没有实际回归。
- 首启语言：chunk-boot 与 bootPlan 都已回落英文；有存档但缺 `langId` 时仍是中文源，与 `setLang` 一致。原生侧与页面看到的是不是同一份语言列表，只有真机能答（`manual-check.md`「23.0 真机核对」第 2 条）。
- 工作流：被 `release.yml` 调用时 `publish` 跳过、并发组不会被取消；PR 上 `inputs.release_tag` 为空。

## 3 · 真引擎走查：「说的对不对」

先说好的，**不要动**：首启对话框有欢迎语、三条路说得清楚；定级结果卡一个大数一个主按钮；课程点错的反馈贴在任务卡下；提示分两步；失着提醒在对手应着之前、应着后自己收起；复盘卡在首屏内、棋盘落在卡片那一步；「你认输时胜率还有 95% —— 这盘本来还能下下去」「第 8 步之前你还领先」这两句是同类产品里少见的好；设置页干净；深色协调；英文不截断；首启 0.5 s 出对话框，复盘 3–5 s。

## 5 · 过程：节奏与真机

- **节奏**：16.0（10-31）→ 23.0（11-14），两周 8 个大版本，其中 20.0 被整版回退。22.0 评估定的「一个大版本至少两周」没有执行。版本号也已经不再表示「改了多少」：23.0 是一个修补版，内容上应该是 22.1。
- **真机**：`docs/manual-check.md` 的「23.0 真机核对」4 条、21.0 起的截图审阅，都没有记录。2.1、2.2 两个问题在真机上 5 分钟就能发现。
- **人工关卡**：`release` 环境还没有设审核人（23.0 的发布作业没有停下等批准就直接发了）。
- **建议**：
  - 修补走小版本号（23.0.1、23.1），大版本只给有主题的改动；
  - 大版本之间至少两周，期间 owner 或 Claude 在真机上把 `manual-check.md` 当版的那一节走一遍，记下结果再发；
  - 给 `release` 环境设审核人。
