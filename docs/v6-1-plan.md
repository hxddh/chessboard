## 0 · 这一版为什么长这样

6.0 是个大版本，§7 的落地记录看起来很齐。复查发现三类问题，按危害排序：

1. **说完成、实际没完成。** 引擎自愈重建不了；`[FEN]` 校验只接在一个对话框上；
   PGN 语料是自写形状用例而不是验收写的公开棋谱库样本。这类最危险，因为它们
   在账本上已经打了勾，没有人会再去看。
2. **换了上游没换下游。** 6.0 把复盘精准度换成胜率口径，判语的档位还留在厘兵
   曲线上；`evalScalar` 把杀棋映射到 9500 以上，厘兵口径的 ACPL 就被灌了水。
3. **验收项没人认领。** §7 开头写「按 §2 的编号逐条对账」，对的是实现项，于是
   §5 的四条验收从来没有对过账，也没有断言。

所以 6.1 不是一堆零散的补丁，它有一条主线：**让账本上的每一个勾都有一条会失败
的断言撑着。** 每修一条缺陷就补一条断言；每一条 §5 的验收都要么被满足、要么被
量出来写明没满足。

## 1 · 丢档（P0）

`persist.js` 的原生镜像是 6.0 的主打功能之一，四条路径会丢用户的档案。

| # | 缺陷 | 修法 |
|---|---|---|
| 1 | 启动先写后读：`loadSettings` / `saveSettings` / 第一次 `saveGame` 都走 `set()`，把 400 ms 的镜像定时器架起来，而 `recover()` 的桥读还在飞。localStorage 被清、文件完好时（正是这个功能存在的理由），读慢于 400 ms 就会让镜像先把默认档写进文件且盖上更新的时间戳，`recover()` 随后读回自己刚写坏的东西，还告诉用户「已恢复」 | `scheduleMirror()` 在 `recover()` 落定前只记待办不落盘 |
| 2 | 恢复后的 1.2 秒窗口：`restoreAll()` 改的是 localStorage，页面仍跑在恢复前的内存状态上，reload 触发 `beforeunload` → `saveGame()`，把默认对局写回刚恢复的键并重新盖戳 | 恢复后冻结一切写入，直到 reload |
| 3 | `restoreAll()` 三处 `storageSet` 不看返回值。恢复是最大的一次写，最可能撞配额；半个档案会被重读并镜像回文件 | 逐个检查，失败则闩锁并返回成败 |
| 4 | `.bak` 只写不读。`APPDATA_BAK` 只出现在写处理器里，注释却说「.bak 是最后一份好副本」 | `appdataRead` 在主文件缺失或零长度时回退到 `.bak`；重命名前 fsync；临时文件名按写次唯一（两个窗口不再共用一个 tmp 并交错字节） |

附带：零长度文件不再等同于「没有文件」（返回 `empty`，按损坏处理并提示）；解析失败
的文件不再静默返回 `none`；隔离区不再被同一个坏值的副本挤掉、也不再被 `clearAll` /
`restoreAll` 清掉；时间戳写失败视为写失败；退出时冲刷待写的镜像。

**验收**：七条单测，覆盖竞态、恢复后覆盖、半个恢复、零长度、解析失败、隔离区、
时间戳；外加恢复路径的 E2E（6.0 完全没有）。

## 2 · PGN 进出（P1）

| 输入 | 6.0 的行为 |
|---|---|
| `1. 0-0+` | 整个文件抛 `unexpected character` |
| `2. -- Nf6` | 抛错，且 `splitGames` 一并抛，多局文件里好的那局也取不出 |
| `1. e4 e5 (1... e5 2. d4) 2. Nf3 Nc6` | 主线变成 `e4 e5 d4`，静默、往返稳定、存盘后永久 |
| 无 `[Result]` 头的 `1-0` | 导出成 `*`（5.2.2 修掉的 D1 在新树路径复发） |
| 超长 token（长网址、十二条箭头） | 吐出超 80 列的行，违反自己声明的契约 |
| 注释里的 `}` | 被改写成 `]` |
| `1. e4 ( {alt} ) e5` | 注释漏到下一个主线着法 |
| `2. exd6 e.p.` / `1. ♘f3` | 致命 |

外加 `[FEN]` 导入不过 `ChessEditor.validate`，而 `fromFen` 经 chess.js 建棋盘，
多出来的王在 `validate()` 看到之前就被吃掉了。

**验收**：每条一份 fixture 或一段测试，回归会当场现形。

## 3 · 引擎生命周期（P1）

`init()` 交出 wasm 后把 `CHESS_SF_WASM_B64` 置空，之后任何一次 teardown 再
`init()`，`loadSources()` 因 b64 已空而不走第一个分支，又因 `sourcesPromise` 仍在
而直接返回那个已兑现的 promise，脚本不再注入，`init()` 抛 `engine sources missing`。
刻意留着「给重建用」的 `wasmBytes` 在抛错那行之后，永远够不着。**6.0 宣称修好的
自愈，实际上一次也愈不了。**

而且两次罢工凑不齐：`onProgress()` 在任何一次 `waitFor` 兑现时清零罢工数，而每次
搜索前都有一次 `isready` 排空。另外三条：teardown 不结算在飞的 `waitFor`，无限分析
期间一次 teardown 会让 `exclusive()` 队列永久卡死；`waitFor` 不记世代，残留定时器
会朝新 worker 记罢工；持续分析的 `stop()` 在自己的搜索还没开始时就发出，会截断别人
的搜索，而被截断的结果按请求预算入了缓存。改 Hash 不清缓存。

**验收**：`scripts/test-engine.mjs`，假 Worker + 手推的虚拟时钟，不需要引擎也不需要
浏览器，全部六条各一段。

## 4 · 复盘的刻度（P2）

判语档位 90 / 75 是照厘兵精准度曲线读的，而 6.0 把喂给 `verdictKey` 的换成了胜率
精准度，那条曲线整体高 10 到 17 点，每个人被高看一档。新档位取胜率曲线上「同样的
棋」所在的位置。

`evalScalar` 把杀棋映射到 9500–9990，杀棋与厘兵之间的跳变被钳成满额漏着记进 ACPL，
赢定的残局里快扫时有时无地报杀就会被记成两个大漏着。两端先各自收进 ±1000 的窗口再
相减。

## 5 · 评级与题库（P2）

6.0 的 `estimateRating` 是「类别基数 + 是否安静着 + 解长」，958 道题因此只落在 10 个
值上：300 道整整 1200，358 道整整 1400。编码的是类别不是难度，「按 ±150 出题」实际
等于「按类别出题」。

改成量出来的序数信号：固定节点预算下的阶梯（引擎的首选第一次等于关键着的那一档），
加首选与次优的分差。用节点不用深度也不用毫秒——毫秒不确定，深度在满级引擎上饱和
（先量过：40 题的样本里 31 题在 depth 1 就是最佳着）。

§5 的另一半验收「每 200 分评级段 ≥ 50 题」6.0 未达也未写；6.1 一并处理。

## 6 · 首屏（P3）

`bundle.js` 1.68 MB 同步加载，约一兆是首屏用不上的数据。`engine.js` 早就有按需注入
的办法，抽成 `chunk.js` 复用；ECO 表（462 KB）先走。两条守卫：分块的负载不得回到
主包，打包清单从 bundler 的 `CHUNKS` 生成而不是再抄一遍。

## 7 · 测试与 CI（P3）

复查时发现的比原来报告的严重：`checks.yml` 的 static 作业手写了三个脚本名，而
`npm run test:static` 列了八个——`test-pgn`、`test-learning`、`test-eco`、
`test-review-winpct` 四个静态测试**从来没有在 PR CI 里跑过**，`test-classics` 更是
写完之后没接进任何地方（而发布说明称它进了 `test:static`）。`release.yml` 同样只点名
`test-chess`。两边都改成跑那个脚本。

`test-mines.mjs` 只打印不断言（§1.2 点名的三个之一，Q0.5 只补了两个），补七条区间。

`test-analysis.mjs` 的语料从 4 局 168 手扩到 28 局约 1300 手——6.0 公布的重合率是从
11 与 14 个事件算出来的。

§5 里四条从未验证的验收（首屏 < 1 s、走一步棋 `draw()` 恰一次、预走 ≤ 1 帧、每 200
分段 ≥ 50 题）各补一条断言，达不到就量出真实数字写明达不到。
