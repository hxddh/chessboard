# 7.3 · 把没人看过的那半个应用修好，再把看得见的那半个做到该有的样子

写在 7.2.0 发布之后、动手之前。规矩和前几版一样：每条说清楚**依据是什么**，
依据是核过的代码、跑出来的数或截下来的图；每条有**验收**；发布前补**落地
记录**，做到的和没做到的都逐条写。

这一版只做两件事：**挖 bug 并修掉**，**把界面与交互做到该有的水准**。不加新
功能——理由在 §7。

---

## 0 · 这一版的由来

7.2 结束时发生了一件事值得当作这一版的出发点：发布前的复查提了三条，三条
都属实，而其中一条顺藤摸出**「接实战」这个按钮从 6.0 起每一次按下去都是当场
抛异常**。替它站岗的，是登记册里一条精确到表达式的源码正则——它匹配的正是
那个读不到东西的表达式。

**形状对，行为错，而且断言写得越精确越像是验过了。**

这一版从这个教训出发，去找**同一类东西**：没有人真的按过、真的看过、真的
量过的地方。找法是三条：

1. 把纯模型喂进边界输入（7.1 的钳制缺陷就是这样找到的）；
2. 把应用**真的跑起来、截下来、量一遍**——这一次第一次这么做；
3. 对着「一条规则在几个地方各写了一遍」的地方逐处比对。

结果：**一个从没有人写过布局的视口类别**，四条确凿的缺陷，以及一份有图为证
的界面清单。

## 1 · P0：竖窗没有布局

### 依据

`styles.css` 里那条把侧栏改成底部抽屉的规则是这样开头的：

```css
@media (max-aspect-ratio: 1/1) and (min-width: 560px) {
```

**`min-width: 560px`。** 比它窄的竖窗，既不走抽屉那一套，也不走窄横窗那一套
（后者要求 `min-aspect-ratio: 1/1`），于是掉回桌面那套：侧栏占 284px，棋盘
分剩下的。实测（面板打开，也就是默认状态）：

| 视口 | 棋盘 |
|---|---|
| 360 × 780（最常见的安卓宽度） | **30 px** |
| 390 × 844（iPhone 竖） | **60 px** |
| 430 × 932 | 100 px |
| 480 × 900 | 150 px |
| 520 × 900（**已发布桌面应用允许的最窄窗口**） | 190 px |
| 559 × 900 | 229 px |
| **560 × 900** | **408 px** |

最后两行是同一件事的两面：**窗口宽一个像素，棋盘从 229 跳到 408。**

而 `chess.panelOpen` 的默认值是「开」，所以在 390×844 上，**首启第一屏就是一块
60×60 的棋盘**；按一下 ☰ 把面板收起来，它才跳回 344×344。

`docs/design-constraints.md` §4 写着「竖窗（`max-aspect-ratio`）改底部抽屉，
不是压窄的侧栏」。这条约束对 ≥560px 的竖窗成立，对手机宽度**从来没有成立
过**——不是被违背，是根本没覆盖到。

### 为什么没人发现

整个 e2e 套件一共实例化 **48 个视口，其中 47 个宽度 ≥ 1200px**；唯一的窄视口
是 `520 × 520`——**正方形**，落进窄横窗那条规则，碰不到竖窗这条路。而已发布的
产品是桌面壳，520×900 这种窗口形状人不常摆。于是这块屏幕没有任何一双眼睛
看过。

### 做什么

1. **给 `< 560px` 的竖窗一套真正的布局。** 抽屉那条规则的 `min-width` 去掉之后
   还不够：它假设抽屉最高 `min(46vh, 430px)`，而 844px 的屏幕减掉 430 的抽屉、
   顶栏与留白，只剩 350 左右——够用但很紧。手机上抽屉应当**覆盖**在棋盘上
   （`position: fixed` + 遮罩），而不是把棋盘挤小：棋盘是这个应用唯一不能被
   牺牲的东西。
2. **棋盘有下限。** 任何视口、任何面板状态下，棋盘边长不得小于 260px；小于
   这个数就该改变布局（收起面板、抽屉改覆盖），而不是继续缩。
3. **默认状态要看窗口。** 「面板默认打开」是为桌面写的。窄窗首启应当默认收起，
   并且把 ☰ 画得足够明显——而不是让第一屏是一块邮票。
4. **顺手用掉那片空白。** 就算布局修好，390×844 上棋盘 344px，上下仍各空
   约 200px。这片空白该给这一页真正需要的东西：走子列表一行、时钟、评估条。

### 验收

- `scripts/test-layout-e2e.mjs` 新增**竖窗组**：360×780 / 390×844 / 430×932 /
  520×900，三语各一遍，面板开与关各一遍。断言：
  - 棋盘边长 ≥ 260px，且 ≥ 视口宽的 80%（面板收起时）；
  - 没有任何元素越出视口（现有的溢出探针复用）；
  - 面板打开时棋盘**不缩小**（覆盖式抽屉的定义）；
  - 首启第一屏就满足上面三条——不需要先按任何东西。
- 这一组测试必须**先红后绿**：在修之前跑一次，把 30px / 60px 那两行记进落地
  记录，再修。

## 2 · 四条确凿的缺陷

### B1 · 一条规则，三处实现，三处不一致（评级）

`picker.js:170` 挑「和你水平相当的题」时，明确把两类排除在外：

```js
const fit = all.filter((p) => !state.solved[p.id] && p.cat !== "mine" && p.cat !== "op");
```

做题页的题面也专门不给开局题显示评级（`app.js`：`p.cat !== "op"` 才追加
「题目 N」）。**作者的意思很清楚：背谱这件事不参与评级。**

但 `ratePuzzleOnce()` 里**一个类别都没排除**。于是：

- 背对一条内置开局线，Glicko 照样动——而界面刚说过它没有评级；
- 7.2 的开局书更糟：`rep` 在 picker 的分档池里**也没排除**，而它的「评级」是
  按**线有多长**推出来的（`puzzleTier` 对开局题按半着数分档，≥9 回合算
  hard = 1800）。**导一本自己写的长变着书，背下来就能把战术评级刷上去。**

**做什么**：把这条规则收进一个地方——`isRatedCat(cat)`，三处都读它。背谱类
（`op` / `rep`）不进评级、不进分档池、题面不显示评级。

**验收**：单测钉住三处读同一个判断；e2e 背完一条开局书的线，`rhist` 不增长、
`rating` 不变。

### B2 · 开局书导入不认 `[SetUp]/[FEN]`

实测：一份从残局局面出发的「体系」PGN

```
[SetUp "1"][FEN "r5k1/5ppp/8/8/8/8/5PPP/R5K1 b - - 0 30"]
1... Rd8 2. Rb1 Rd2 *
```

被 `repertoire.js` 读成一条线 `"Rd8 Rb1 Rd2"`，而这三手**从标准开局根本走不
出来**（已在 node 里验过：第一手就非法）。这条线照样进书、照样铸成一道题，
而那道题谁也做不了，界面一个字都不说。

7.1 在棋谱库那条导入路径上修过**同一类缺陷**（`foldGame` 不读起始 FEN）。新
写的这条路没接上那个教训。

**做什么**：导入时跳过带 `[SetUp]` 的局并说明原因（「开局书是从起始局面开始的
一串着法」），或者把起始局面一并存下来并让树从它出发——前者一行，后者是新
能力。**这一版选前者**，理由写在代码注释里。

**验收**：单测——带 SetUp 的 PGN 进来，`linesFrom` 一条都不产出；e2e——导入
这种文件，书没变大，且页面说了为什么。

### B3 · 记录页的缺口行会折成两行

截图为证：`D30 Queen's Gambit Declined` 这一行，名字折到第二行，右边的
「12 局 · 输 12」也跟着折成「12 局 ·」/「输 12」两截。`stat-k` + `stat-v` 这
套两列行是为短标签写的，284px 的栏里放不下 ECO 全名。这是 7.2 自己留下的。

**做什么**：长名字单行截断 + `title`，右列固定宽度、数字右对齐、tabular
数字。这条不是孤例——见 §4 的 A 组，整页的行都要按同一套规则收口。

### B4 · 做题页同一句话出现两遍

顶栏左上角：「实战里你走了 d3 —— 找出更强的一手 · 当时亏 3.2 分」
右栏题面：「第 1 题 · **实战里你走了 d3 —— 找出更强的一手 · 当时亏 3.2 分** ·
题目 1500」

一字不差，同屏两处。顺带，那个「题目 1500」正是 B1 里说的那个不该存在的数。

**做什么**：顶栏说「你在做第几题、目标是什么」，题面说细节与来源，两者不重复。

## 3 · 系统性：登记册里守着「动作」的那些断言

`scripts/test-chess.mjs` 现在有 **124 条**源码正则断言。7.2 刚证明了其中至少
一条**守着一个从 6.0 就坏掉的按钮**，而且守得「很精确」。

登记册这个做法本身是对的（它的注释自己论证过：这些断言锁的是形状，是搬代码
时最大的阻力，也是最大的虚假安全感，所以只减不增）。这一版要做的不是删掉它
们，而是**按危险程度排序地换掉**：

- **守着「用户能按的东西」的断言**（按钮的处理函数、菜单命令、对话框的开关）
  ——形状对不代表按得动，7.2 的教训就在这一类里。这一版把这一类逐条换成真去
  按的浏览器测试。
- 守着纯数据形状的（表格、常量、ID 方案）留着——那些正则和行为之间没有缝。

**做什么**：先把 124 条分类并写进登记册注释（每条标 `action` / `shape`），再
按 `action` 那一类逐条替换，登记册相应下调。

**验收**：`action` 类清零或给出剩余名单与理由；登记册数字下降，且每下降一条
都有一条对应的行为测试进来。

## 4 · 界面与交互：做到该有的样子

下面每一条都有截图为证（`scratchpad/shots/*.png`，发布前整理进
`docs/review-v7.md`）。这一节的目标不是「重画一遍」，而是**把已经很好的部分
之外那些明显不及格的地方收口**——棋盘本身、四套主题、棋子与坐标是这个应用
最好的部分，不动。

### A · 数据展示：一套规则，不是二十处即兴

**现状**：记录页五个小节各有各的结构——有的把数值放在标题右边，有的放在行
右边，有的直接写成正文；数字与单位之间的空格不一致（「1胜 0负 0和」）；长
名字折行（§2 B3）；提示文字与内容文字几乎同一号。

**做什么**：定义**三种行**，全页只用这三种：
1. `label → value`（右列定宽、tabular 数字、单位统一）；
2. `label → value + 一句解释`；
3. 纯段落（提示）。

字号与颜色各自固定（沿用既有的 7 档字号，不新增档位——见
`design-constraints.md`）。

**验收**：记录页与诊断页的每一行都属于这三种之一（e2e 遍历 DOM 断言）；三语
各跑一遍，**没有任何一行折行**；数字列在同一小节内左边缘对齐（量像素）。

### B · 诊断页的三张图重做

**现状**（截图）：

- **分阶段柱**：开局 8、中局 8、残局 93。线性比例下前两根塌成 1px 的横线，
  数字浮在空中——读起来像「两个空槽和一块红砖」。
- **失误分布**：三根细柱孤零零地悬在一大片空白里，没有基线、没有坐标，只有
  左右两个「1」「36」。
- **开局战绩**：两根满宽条，一根米色一根红色——因为胜率 100% 与 0% 各自把整
  条填满，两条看起来只是颜色不同；没有图例，下面的列表又把同样的数字念了
  一遍。

**做什么**：
- 每根柱有**最小高度**（≥4px），让「小」和「没有」在视觉上是两件事；
- 有基线、有刻度上限标注；
- 开局战绩改成**胜/和/负三段**并给图例，或者干脆退回到排好版的列表——两者
  都比现在诚实。哪一种，发布前对着截图选，理由记进落地记录。

**验收**：e2e 量每根柱的高度 ≥ 4px 且 ≤ 画布高；同一张图里最大值与最小值的
高度比不超过画布允许的范围（不再出现 1px 线）；三张图各自有 `aria-label`
（已有）且**图里出现的每个数字都能在页面文字里找到**（图不是唯一信息源）。

### C · 棋谱库列表

**现状**（截图）：行被硬生生截断在滚动区下边缘（半行「负 · rival17」）；
「再深一遍」按钮游离在行卡片之外、重复 24 次，比棋局本身还显眼；三组筛选
段控件宽度参差，右边缘不齐。

**做什么**：滚动区给渐隐边缘与明确高度；动作收进行内（次要样式）；三组段控件
等宽网格（`design-constraints.md` §4 已有这条规矩，这里没遵守）。

**验收**：e2e 断言三组段控件右边缘同一像素；列表底部行不被半截切断（滚动容器
高度是行高的整数倍，或有渐隐）；行内动作不参与 tab 序的主路径。

### D · 顶栏：一处只说一件事

**现状**：顶栏一行里挤着状态 chip、执子、玩家名、最后一手、引擎名与难度、
一个方框「行」、两个王的字形——八样东西同一号字，没有层次；而其中一样（题面）
和右栏一字不差地重复（§2 B4）。

**做什么**：定出顶栏的三段职责（**谁在走 / 这是什么局 / 现在能做什么**），
每段一个视觉层级；其余移回它该在的地方。

**验收**：三语 × 四视口截图对照；e2e 断言顶栏文本与右栏首行文本没有 ≥8 字的
公共子串。

### E · 内容页的宽度

**现状**：在「记录」和「做题」页，棋盘仍占桌面 **54%** 的屏幕，而这一页真正的
内容挤在 284px 的栏里折行。棋盘在这两页不是主角。

**做什么**：内容页让面板可以展宽（或棋盘让位），这是这一版**唯一的结构性改
动**，也是最能改变「质感」的一条。具体形态先出三个方案的截图再定。

**验收**：记录页在 1400×900 下内容区 ≥ 520px 宽；切回对局页棋盘尺寸不变；
现有 layout e2e 一条不改地全过。

## 5 · 查过、没问题的（免得下一版再查一遍）

- **横向溢出**：三语 × 四视口（390 / 820 / 1400 / 1400-en）逐元素量过，
  **没有任何元素越出视口**。
- **注解很多的 PGN 会不会把开局书撑爆**：8 / 14 / 18 个分支点的真实形状实测，
  枚举 + 入书合计 < 20ms，条数线性增长（变着是兄弟节点不是乘数）。不是问题。
- **四套主题的棋子对比度**：6.x 实测 5.86–17.72:1，本版不动棋盘绘制，沿用。

## 7 · 明确不做

- **不加新功能。** 这一版是「修 + 收口」。7.2 刚加了两件大东西（开局书、库的
  再分析），它们的接缝正是这次复查抓到三条的地方——再叠一层新功能，只会让
  下一次复查有更多接缝可抓。
- **不重画棋盘、不换棋子、不动四套主题的色板。** 那是这个应用现在最好的部分。
- **不引入任何 UI 框架或组件库。** 现有的 token 体系（7 档字号、3 档行高、一条
  缓动曲线）已经够用，缺的是**遵守**，不是更多机制。
- **不动移动端打包。** §1 修的是布局规则，不是上架移动端——那是独立的一件事
  （见 `docs/` 里那份可行性评估）。

## 8 · 落地记录（7.3.0）

### §1 竖窗布局（P0）

`src/web/styles.css` 新增一条窄竖窗规则，媒体查询 `(max-aspect-ratio: 99/100)
and (max-width: 559.98px)`；`app.js` 用同一条查询字符串常量 `SHEET_QUERY` 问
`matchMedia`，两处一字不差由 `test-chess.mjs` 守着。

取 `99/100` 而不是 `1/1`：520×520 是正方窗，不是竖窗，按抽屉排会在棋盘下留一条
245px 的空带（这条是写完第一版后被既有测试当场抓到的）。

**做法**：抽屉高度 `--sheet-h: min(46vh, 430px)` 常驻——棋盘按
`100vh − chrome − sheet − 2·pad` 算，所以开合面板棋盘一样大。这是这条修法的
关键：让出高度是一次性的，盖上来是免费的。

**实测（首启第一屏，棋盘边长）**

| 窗口 | 改前 | 改后 |
| --- | --- | --- |
| 360×780 | 30px | 314px |
| 390×844 | 60px | 344px |
| 430×932 | 100px | 384px |
| 520×900 | 190px | 408px |
| 559×900 | 229px | 408px |

559→560 那道一像素断崖消失，两边都是 408。开合面板棋盘大小在四档尺寸上全部
相等。测试：`test-layout-e2e.mjs` 竖窗组（四档尺寸 + 390×844 三语）。

### §2 四条缺陷

- **B1**：新增 `isRatedCat(cat) = !isOpeningCat(cat)`，评级写入、任务行显示、
