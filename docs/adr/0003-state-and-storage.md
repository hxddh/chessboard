# 0003 · 状态与存储：一个 store、一张事件表、原生 SQLite

**状态**：已定（2026-11-06）。

## 背景

- 19.0 的状态是 3 块可写对象、111 个字段，51 个文件直接赋值；一次提交让整块的订阅者全部重跑；没有「上一个状态」。
- 存档三层：浏览器缓存（localStorage）+ 原生文件（每键 A/B 两代 + 清单提交）+ IndexedDB（再镜像成 68 个分片），按 `writtenAt` 对账；约 2,800 行代码、约 3,000 行测试。
- 一盘 160 步的棋自动存 160 次，每次整份重写，共 3.3 MB。
- 进度散在 `learn`、`puzzles`、`mines`、`progress`、`achv` 几个键里，`planner.js` 各读各的，所以没有一个地方知道「这个人会什么」。
- 20.0 不读旧档案（v20-0-plan §0、§8 第 7 条），可以从零设计。

## 决定

- **一个 store**：状态是不可变的普通对象；改动只通过具名动作（`play.move`、`review.open`、`learn.answer`…）；界面用 selector 订阅自己要的那一片（配合 ADR 0002 的信号）。每个动作有前后两个状态，动画和撤销都从这里来。
- **一张事件表是事实来源**：凡是「发生过的事」都追加一条事件——走了一步、答了一题、复盘发现一处、完成一课、改了设置。其他表都是事件的投影，任何时候可以从事件重算。
- **原生 SQLite**：用 SDK 的 RelationalStore（`app.zon` 声明 `sqlite` 能力；sdk-fork 的 R01 由「不抄」改为「照抄上游」）。表：
  - `events`（只追加）
  - `games`、`moves`、`analysis`（复盘结果，重开还在）
  - `skills`、`cards`（学习者模型与间隔复习，ADR 见 v20-0-plan §2）
  - `repertoire`、`library`（导入的对局）、`settings`
- 网页通过一个很薄的 `db` 服务访问：`append(event)`、`query(name, params)`；写入批量合并（一帧内的多条事件一次落盘）。
- **迁移只往前**：从 20.0 的 schema v1 开始，每次改表写一个往前的迁移；不写回退，不读 19.0。
- **导入**：一次性导入 PGN（含 19.0「导出全部数据」里的对局），导入的对局照常喂给学习者模型。

## 后果

- 删掉：`persist.js` 的三层对账、A/B 两代、68 个分片、`quarantine`、存档槽、所有 `chess.*` 键与它们的测试。
- 自动存档一步只追加一条事件：一盘 160 步写入总量 ≤ 100 KB（v20-0-plan §1 验收）。
- 学习者模型、今日一课、复盘结果都在同一个库里，跨页面一致（修走查的 B1、B10）。
- 风险：网页 ↔ 原生的调用延迟。对策：读在启动时批量取进内存，写批量合并；性能 e2e 守每步开销 ≤ 6.5 ms。
- 浏览器里跑的 e2e 没有原生端：`db` 服务另有一个内存 + IndexedDB 的实现，只给测试和开发服务器用，接口与 SQLite 版一致，有同一套契约测试。

## 不做的选择

- **只用 IndexedDB**：WebView 的网页存储可能被系统清理，这正是 7.x 起加原生文件的原因；不能把唯一的一份放在那里。
- **原生文件存 JSON**：要自己做事务、自己做索引，等于再写一个小数据库。
