# 8.0 · 从一块棋盘到一个完整的棋类应用

写在 7.9.0 发布之后、动手之前。规矩照旧：

- 每条写**依据**、**做什么**、**验收**；
- 发布前补**落地记录**，做到的和没做到的都逐条写。

这一次不是一个版本的计划，而是一个大版本的路线图。7.7–7.9 三轮打磨已经把「一块棋盘加一条侧栏」做到了很高的完成度，再做第四轮像素修整，收益已经很小。8.0 要回答的问题换了：**用户打开这个应用，能不能像打开 Lichess 或 Chess.com 一样，找到一整套下棋、训练、复盘、管理自己对局的东西，而且每一样都做得扎实。**

## 依据：四路深度评审

四路评审并行进行，每一路都有实测和截图，都没有改动任何受版本控制的文件。原始报告与截图在会话的临时目录里，这里只收结论和关键数字。

1. **产品与体验**：
   - 用真 Stockfish 把主要流程从头走到尾：
     - 首次启动；
     - 人机对局（初级·贪吃子·5+3）；
     - 复盘；
     - 棋谱库：导入 28 局，离线分析 264 秒；
     - 做题、教学、双人、开局库、设置。
   - 对照 Lichess、Chess.com、ChessBase、En Croissant、Chessable。
2. **工程**：
   - 量了每步耗时、启动、内存、包体、引擎吞吐与锁、存档与备份上限、CI 各 job 时长；
   - 读了原生壳、存档、测试基础设施。
3. **棋力与训练深度**：
   - 清点了对手、复盘、课程、题库、开局的内容量；
   - 引用 `measured.json` 的强度与可复现性数据；
   - 用引擎在 16 层深度抽检了 60 道挖掘题。
4. **视觉与交互**：
   - 22 张固定截图，另补拍 45 张：四套主题 × 两套棋子、对话框、悬停与焦点、1280 / 1920 宽窗、动画帧；
   - 看了设计 token、棋子与棋盘资源、图标。

**评审的局限**：截图用的是无头 Linux 的字体；WebKit 只在 CI 上跑过；声音没有用耳朵听；绝对性能数字只用来比较量级，真机上要复核。

## 0 · 结论先行

### 已经是强项、8.0 要保留的

- **「为什么」加「再试一次」的复盘**：只说确定的事实（「对方 dxc4 之后丢象」），不编理由。这份克制是和 Chess.com 的差异点。
- **一条完整的离线闭环**：棋谱库 → 批量分析 → 诊断 → 错题本 → 间隔重复 → 今天的训练。这正是 Aimchess 一类产品收费的东西。
- **内容的正确性**：题目有求解器门禁和引擎复核（抽检 60 道，没有一道存的是更差的解法）；档位强度实测过。
- **工程纪律**：
  - 三语，键盘全程可用；
  - CSP 严格，源码里 `innerHTML` 为 0；
  - 原子写与损坏隔离，长对局没有内存泄漏；
  - 设计 token 与字号、时长、颜色都有守卫。
- **棋盘手感**：拖拽、盘上升变、对阵条、木质音效。

### 差距在哪里（按影响排）

1. **产品结构**：
   - 整个应用是一块棋盘加三个页签的侧栏，没有首页；模式开关放在「设置」里；棋谱库和诊断是约 460px 宽的弹窗，诊断的右列被截断。
   - Lichess 和 Chess.com 顶上都有一条导航：下棋、谜题、学习、分析、资料库、个人主页。
2. **内容量与深度**：
   - **题库**：共 1,170 道，**全部是白先**（黑先的题被镜像成白先），68% 一步就解完，≥ 2200 分的只有 73 道，没有计时冲刺模式。仓库里写好的 Lichess CC0 导入器从没产出过数据。
   - **复盘**：
     - 分析用 `go movetime`，同一局跑两次，`?!` 的一致率只有 38%，`?` 58%；
     - 只能认出 5 种战术母题，覆盖全部失误的 22.7%；
     - 走查里还有一例把「马没保护被吃」说成「牵制」。
   - **对手**：
     - 6 档，休闲到入门之间有断崖（对「不送子」机器人的得分从 29% 掉到约 0%）；
     - Elo 标签没有校准过；
     - 玩家没有自己的对局等级分；
     - 棋钟最长 10 分钟。
   - **你自己的对局**：
     - 棋谱库上限 500 局、不能搜索，「对局历史」和「棋谱库」是两份列表；
     - 导入后必须手填名字，否则什么都不算；
     - 没有开局浏览器；
     - 不能从 Lichess / Chess.com 账号拉棋。
3. **外观停在「正确」，没有到「好看、有辨识度」**：
   - **布局**：不随窗口伸展，1920 宽时左右各空 258px；侧栏里棋谱结束后到翻谱栏之间空约 380px。
   - **棋盘与棋子**：
     - 默认棋子是 cburnett 的重绘版，1× 下黑王的白色外轮廓粗得像白王；
     - 17px 木框像玩具棋盒；
     - 「日」和「木」几乎是同一块棋盘，「纸」没有纸感；
     - 同一种标记落在深格和浅格上是两种颜色。
   - **关键时刻**：做题解出时，棋盘上唯一的信号是红色的将军光晕；终局、成就都没有在棋盘上当场回应。
   - **复盘界面**：Chess.com 的旗舰恰好在这里，差距最大。
   - **图标**：图标里的马读起来像独角兽。
4. **工程上会拖住 8.0 的**：
   - **备份与恢复对重度用户是坏的**：原生读文件上限 256 KiB、写 384 KiB，光是 500 局对局记录导出来就约 327 KB，超过上限的导入直接被拒；
   - **走一步棋的开销随对局长度平方增长**：每步脚本时间从开局的 13.5 ms 涨到第 140–160 手的 65 ms，原因是游戏树只存 SAN，识别开局、重复计数、翻谱都要从头重放；
   - **引擎是一把全局锁**：分析中走一步要等 2.7 s；
   - **`app.js` 太大**：11,665 行、444 个函数，是每次并行合并的冲突源；
   - **CI 太慢**：关键路径是 32 分钟的布局测试，每个提交跑两遍；Windows 原生在 PR 上从不编译。

### 8.0 的主张

三根支柱加一层地基。每一根都要让用户一眼看出「这是一个大版本」：

| | 支柱 | 一句话 |
|---|---|---|
| **地基** | 工程 | 先把会拖住后面一切的东西修掉：CI、游戏树、备份、`app.js` 拆分的第一步 |
| **A** | 结构与外观 | 有首页和导航；布局随窗口伸展；新棋盘与棋子；复盘做成一张一眼能读懂的体检报告；关键时刻在棋盘上当场回应 |
| **B** | 训练 | 题库扩大一个数量级并按原执子方出题；复盘可复现、会分级、会讲更多种战术；有标定过的对手阶梯和你自己的等级分 |
| **C** | 你的棋 | 棋谱库做成真正的数据库（可搜索、上万局）；可选地从 Lichess / Chess.com 同步；开局浏览器 |

## 1 · 地基：先修会拖住 8.0 的

### F1 CI 提速、去重，并在 PR 上编译 Windows 原生【S】

**依据**：

- PR 的 checks 墙钟约 28–46 分钟。关键路径是 `browser (chromium, panel layout)`：31 分 51 秒。
- 每个提交同时触发 push 与 pull_request 两次 checks。
- 静态测试（含 150 题抽样校验）在三个操作系统上各跑一遍，约 7.5–9 分钟；抽样校验与平台无关。
- `build-windows.yml` 只有 `workflow_dispatch` 与 `workflow_call`，PR 上从不编译 Windows 原生。5.0–5.2 连续三个版本出过的 Windows 对话框和 Escape 问题，就是这个盲区造成的。

**做什么**：

- `test-layout-e2e` 按 `SHARD=i/n` 切 3–4 片，进 CI 的 matrix；
- `on: push` 只留 main；
- 挖掘题抽样校验只在 ubuntu 上跑；
- 加 `concurrency: cancel-in-progress`；
- zig job 加一行 `windows-latest`，跑 `zig build test`。

**验收**：

- 前后各 5 次运行对比：PR 墙钟 ≤ 15 分钟，runner 分钟数约减半；
- 静态守卫断言 checks.yml 里有 Windows 的 zig 编译。

### F2 游戏树带局面，每步开销回到 O(1)【S–M】

**依据**：

- 实测每步脚本时间：13.5 ms（第 1–20 手）→ 65 ms（第 140–160 手，p90 86 ms）。
- 在回放里按一次方向键约 23 ms。
- 性能剖析里的大头：
  - `renderOpening` 每次提交把整局重放两遍，约 21 ms；
  - `viewGame` 约 15 ms；
  - `repetitionCount` 约 11 ms。
- 160 步写了 320 次 localStorage，共 3.23 MB。

**做什么**：

- 树的每个节点缓存四样东西：`fen`、`positionKey`、重复计数签名、已识别的 ECO；
- `viewGame`、`gameAt`、`openingFor`、`repetitionCount` 都改为按节点 id 查表；
- 存档写入改为只在内容真的变了时写。

**验收**：新增 `scripts/perf-e2e.mjs`（只跑 Chromium，约 2 分钟），作为门禁：

- 第 160 手每步脚本时间 ≤ 第 20 手的 1.5 倍；
- 回放每步 ≤ 5 ms。

### F3 备份与恢复修好，存档分片【M】

**依据**：

- 原生 `readTextFile` 上限 256 KiB（`src/main.zig:393`），`writeTextFile` 上限 384 KiB（`:395-396`）。「导出全部数据」和「导入全部数据」都走这两个命令。
- 500 局对局记录导出约 327 KB；再加上棋谱库与分析，导出只能退回「复制到剪贴板」，导入直接被拒。
- 每次 `Persist.set` 都会在 400 ms 防抖后把**整份存档**转成 base64 过桥写盘。编码耗时实测：
  - 0.5 MB：26 ms；
  - 2 MB：86 ms；
  - 6 MB：355 ms。
- `SCHEMA = 1`，唯一的迁移什么也不做。
- 没有任何测试覆盖「导出一份大存档再导回来」。

**做什么**：

- 原生读写改为分块或流式，上限 ≥ 16 MB，缓冲从栈改到堆；
- 导出改用紧凑 JSON；
- 原生镜像改为每个键一个文件，只写变过的键；base64 改为分块或移出主线程；
- `SCHEMA` 升到 2，写真正的迁移。它也是 C1 数据库化的前提。

**验收**：

- `test-persist-e2e` 新增：导出 2 MB 存档 → 清空 → 导回 → 逐键相等；
- Zig 单元测试覆盖 2 MB 往返；
- 主线程上单次镜像写入 ≤ 16 ms。

### F4 `app.js` 拆分的第一步：先让测试不绑文件名【M，持续进行】

**依据**：

- `app.js` 11,665 行、444 个顶层函数。6.1 定的「< 4000 行」目标此后反而涨了 2,750 行。
- 7.9 的四块并行开发里，冲突全在它和 `styles.css` 上。
- `test-chess.mjs` 有 86 处读 `src/web` 源码做正则匹配，函数一搬文件，这些断言就会变红。

**做什么**：

1. 先把正则断言改为按符号或模块定位，不再写死文件名（「源码正则登记册」只减不增的规矩照旧）；
2. 沿用 `createLibraryUI(d)` 的做法（显式传入依赖），依次拆出：
   - `review/`：分析、复盘、再试一次，约 1,700 行；
   - `trainer/`：课程、题目、今天的训练，约 2,600 行；
   - `game-controller`、`settings-ui`、`io`。
3. 每个 PR 只搬一个模块，行为零改动。

**顺序约束**：A、B 两根支柱都要在这些模块里动手，所以要**边做边拆**。动哪块，先把哪块拆出来。

**验收**：

- 新增「`app.js` 行数只减不增」的登记；8.0 结束时 ≤ 6,000 行（4,000 仍是目标）；
- 每一步 CI 全绿。

### F5 首屏与包体【S】

**依据**：

- 首次加载时，12 张棋子 SVG 每触发一次 `onload` 就清空精灵缓存、重画整盘，一共画了 12 次，每次约 200 ms（量级可能被无 GPU 环境放大，真机要复核）。
- `bundle.js` 1.71 MB。其中教学内容（三种语言）787 KB，占 46%；i18n 三套字典 171 KB；`puzzles-mined.js` 176 KB。
- 6.1 就计划过按语言分块，但 `CHUNKS` 里至今只有 ECO 一项。

**做什么**：

- 12 张棋子图全部 `decode()` 完成后只画一次；
- 非当前语言的内容和挖掘题进分块（`chunk.js` 已经有加载机制）。

这也是 B1 题库扩容的前提：新题库必须按需加载，不能进主包。

**验收**：

- 主包减少 ≥ 40%，由包大小预算的守卫盯住；
- 就绪时间前后对比；
- 首屏只重画一次，用断言检查。

## 2 · 支柱 A：结构与外观

### A1 首页与顶层导航【L】

**依据**：

- 模式分段控件在设置页里（`index.html:171`）。
- 棋谱库和诊断是约 460px 的弹窗（`index.html:1027`、`:1066`），诊断的右列被截断，列表一屏只放得下 5 局。
- 「记录」页把统计、棋谱库、开局库、对局历史、成就五块竖着堆在 400px 宽的侧栏里。
- 首次启动选「我会下棋」之后，直接按初级、执白、无棋钟开局，不问任何选项。
- 一步未走时「新局」按钮是隐藏的（`app.js:7891`）。

**做什么**：

- **导航**：左侧窄栏（宽窗）或顶栏（窄窗），入口依次是 下棋 / 谜题 / 学习 / 棋谱库 / 我的。
- **首页**：三张卡——「继续上次」「今天的训练」「下一步建议」。
- **模式**：从设置页移出。
- **整页视图**：谜题、棋谱库、诊断、开局库、「我的」改成整页，棋盘缩到左侧或隐藏。
- **下棋视图**：保持现在的几何，对局中用户最熟悉的画面不动。
- **设置**：只留对局相关的项。外观、语言、声音进偏好窗口，macOS 用 ⌘, 打开（设计评审 #10）。

**验收**：

- 从首页到每种模式都是一次点击；
- 三种窗口形态（宽、窄、竖）各有截图基线；
- `test-layout-e2e` 的对局视图断言不变或只收紧。

### A2 布局随窗口伸展【L】

**依据**：

- 1920 宽：左右各空 258px，侧栏被 `clamp(284px, 30vw, 440px)` 卡在 440px。
- 棋谱两列相距约 175px。
- 翻谱栏钉在面板底部，和棋谱最后一行之间空约 380px。
- 竖窗 600×900：底部抽屉第一屏只露出约 240px，棋谱在屏外。

**做什么**：

- **宽窗（≥ 1280）**：左信息栏（对手、棋钟、开局名）+ 居中棋盘 + 右栏（棋谱、复盘）。右栏随宽度伸展到约 520px。
- **棋谱**：改为紧凑的三列表（回合号、白、黑），列宽按内容，隔行加底色；变着缩进加一条竖线；翻谱栏跟着棋谱底部走。
- **竖窗**：棋盘 + 一条横向滚动的棋谱 + 抽屉。

**验收**：在 1024 / 1280 / 1440 / 1920 / 600 五档宽度下：

- 非内容空带 ≤ 48px；
- 棋盘占比不低于现在；
- 1440 下棋谱两列间距 ≤ 40px；
- 翻谱栏与最后一行棋谱的距离 ≤ 16px。

### A3 棋盘与棋子的新材质，主题体系重构【M】

**依据**：

- 默认棋子 cburnett 的重绘版线条粗；1× 下黑王像白王。
- 只有两套棋子。
- 木框 17px，加 145° 渐变和 36px 投影。
- 四套主题实际只有三块棋盘：「日」和「木」的格子色几乎相同。
- 同一种标记在深浅格上是两种颜色。7.8/7.9 量了色度上限，没量深浅格之间的一致性。

**做什么**：

- **默认棋子**：换成许可相容的精修版本（Wikimedia 原版 cburnett，或 Lichess COPYING 里 GPL / Apache / CC BY(-SA) 的候选，逐套核许可）。另外加 4–6 套已核许可的棋子。
- **默认棋盘**：改为平盘、2–4px 圆角，坐标默认写在盘内；木框保留为选项。
- **主题拆成两个维度**：
  - 外观：浅色 / 深色 / 跟随系统（默认跟随）；
  - 棋盘：木、绿、蓝、纸墨、大理石等 5–6 块。
- 「纸」做成真正的纸纹加墨色棋子。
- 旧的 `themeId` 迁移到新的两个维度。

**验收**：

- 每块棋盘都有标记色度上限和深浅格 ΔE00 上限，写进 `measured.json`；
- 新旧 `themeId` 有迁移测试；
- 1× 截图盲测能认出黑王。

### A4 复盘模式重做【L】

**依据**：

- 评估条是外框左侧约 12px 宽的一根白条，没有对齐外框（外框 y=72，条从 y=89 开始）。
- 胜率曲线约 120px 高、灰色填充，没有白黑分色，也没有坐标。
- 失着只在棋谱里有一个很小的 `?` / `??` 后缀，棋盘格子上没有徽标。
- 「关键一步」「收进错题」用的是虚线卡片，看上去像占位符。
- 「重下」和「再试一次」并排、名字相近。走查时点了「重下」，得到的是一个意料之外的确认框。

**做什么**：做成独立的复盘视图，一张「对局体检报告」：

- 顶部：双方精准度与着法分级计数（分级规则见 B2）；
- 大号胜率图：白黑分色，失着点可以点；
- 棋盘上：在目标格角上标 `?? ? ?!`；评估条收进外框；
- 棋谱：按分级着色；

### A5 关键时刻与动效【M】

**依据**：

**做什么**：

- **终局**：王的格子上出结果徽标，结果卡浮在棋盘上。
- **做题对错**：目标格角上出绿 ✓ 或红 ✗ 徽标。

- **不撒花**：7.7 §11 的规矩照旧。
- **按钮收干净**：终局后和打开历史对局时隐藏「悔棋」「再来一盘」。

**验收**：

- 棋盘上不再出现「成功用红色」；

- 用 60fps 录屏逐帧检查。

### A6 品牌、图标与窗口外框【M】

### B2 复盘可复现、更深，并补全着法分级【M】

**依据**：

### B3 教练解释 2.0【M】

**依据**：

- `motif.js` 只认 5 种母题：捉双、牵制、串击、闪击、双将。
- 能说出母题的：全部失误的 22.7%，严重失误的 29.8%。
- 走查里有误报：4.Ng5?? 被说成「漏看了 ♛xg5 牵制」，实际只是马没保护被吃。
- 7.1 的 CHANGELOG 自己写着「正确性没有人工抽样核对过」。

**做什么**：

1. **先核对**：人工抽样 100 条现有说明，量出误报率。
2. **修误报**：先修「牵制」一类的误判。
3. **再扩母题**：从 5 种扩到约 14 种——挂着的子、底线弱点、杀棋威胁、被困的子、消除防守者、过载、引离、引入、X 光、中间着、绝望子、升变、长将。
4. **说威胁**：新增「忽略了对方的什么威胁」，用空着搜索或对方的最佳着来判断。
5. **原则照旧**：不确定就不说。

**验收**：

- 严重失误的母题覆盖率 ≥ 55%；
- 人工抽检 100 条，说错的 ≤ 5%；
- 达不到时，该母题回退到只说子力得失。

### B4 对手阶梯、角色与你的等级分；时间控制补全【M】

**依据**：

- 6 档；休闲到入门之间有断崖（对「不送子」机器人的得分：29% → 约 0%）。

- **角色**：档位 × 风格包装成 8–12 个命名角色，配图标头像，一句开场白、一句终局评语。

- **认输和提和**：引擎在明显输定时认输，在死和局面里提和。

**验收**：

- 新增阶梯测量：相邻两档强者得分在 60–75% 之间，整条阶梯单调；
- `test-strength` / `test-novice` 按新档位重新标定；

## 4 · 支柱 C：你的棋

### C1 棋谱库数据库化【L】

**依据**：

- 上限 500 局（`library.js:35`）。
- 存储是 localStorage 加一份整份 JSON 的原生镜像，受约 5 MB 配额限制。

**做什么**（依赖 F3）：

- **存储**：改为原生文件或 IndexedDB，按局分片，上限 ≥ 1 万局。
- **搜索**：对手、开局 / ECO、日期、结果、执子方、时控、「包含这个局面」。

**验收**：

### C2 从 Lichess / Chess.com 同步（可选联网）【M】

**依据**：

- 唯一的来源是「导入棋谱文件」：先去网站导出、下载、再导入、手填名字，一共 5 步。
- 7.0 立下的主张是「任何人 99% 的对局在别处」。
- 原生壳已经有 HTTPS 客户端（`src/main.zig:1001-1015`，现在用来检查更新）。
- 页面的 CSP 是 `connect-src 'self'`，应该保持不变。

**做什么**：

- 输入用户名，由**原生层**拉取最近 N 局，走公开接口：
  - Lichess：`/api/games/user/{name}`；
  - Chess.com：`/pub/player/{u}/games/archives`。
- 拉到的对局自动认领名字，自动排进分析队列。
- 设置里加「允许联网同步」，**默认关**；只在用户主动触发时请求，不带任何标识。

**验收**：

- 原生层有单元测试，覆盖两种接口的应答解析（用固定样本）；
- 断网、速率限制、用户名不存在各有提示；
- 页面的 CSP 不变，由静态守卫盯住。

### C3 开局浏览器【M–L】

**依据**：

**验收**：
